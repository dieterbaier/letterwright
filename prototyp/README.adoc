= Prototyp: Vorlagenformat und Rendering

Wegwerf-Prototyp für https://github.com/dieterbaier/standardschreiben/issues/3[#3]. Er
prüft ADR-003, ADR-004, ADR-005 und ADR-014 an der DOCX-Vorgabe unter `src/examples/`.
Der Code wird nicht ins MVP übernommen und liegt deshalb außerhalb des Gradle- und
npm-Builds. Der Wurzel-Build bindet nur die Module unter `src/application/backend` ein.

== Funktionen und Grenzen

Was der Prototyp zeigt, was nur mit Einschränkung geht und was nicht gelungen ist. Die Spalte
„Nachweis“ nennt den Befehl oder den Test, der den Stand belegt; die Abschnitte weiter unten
erklären die Einzelheiten. Der Stand ist der eines Wegwerf-Spikes: Er belegt Machbarkeit, keine
Produktqualität.

Nicht gelungen oder bewusst nicht gemacht:

* Die Fußzeile ohne Nachbearbeitung zu taggen. openhtmltopdf hat dafür keine Einstellung, und
  als Inhalt der ersten Seite schiebt es sie auf Seite 2.
* Reflow bei 200 % Zoom. Die Vorschau zeigt ein festes A4-Blatt; sie scrollt stattdessen, auch
  per Tastatur (Ausnahme für zweidimensionale Inhalte in WCAG 1.4.10).
* Durchgehendes Vorlesen über Seitenwechsel mit VoiceOver. Nicht weiter untersucht.
* Eine gleich breite freie Ersatzschrift für Arial Narrow. Es gibt keine.
* Die Messung der Bildschirmdarstellung der Vorschau gegen das PDF (QS-004).

== Schriften

Nach ADR-017 ist der Ordner des Hosts die einzige Schriftquelle. Der Prototyp liest jede
`.ttf` und `.otf` aus `schriften/` und nimmt Familie, Gewicht und Stil aus der Datei selbst.
Lizenzpflichtige Schriften werden nicht eingecheckt. Auf macOS lässt sich der Ordner mit den
Systemschriften füllen:

[source,sh]
----
mkdir -p schriften
for f in "Arial" "Arial Bold" "Arial Italic" "Arial Bold Italic" \
         "Arial Narrow" "Arial Narrow Bold" "Arial Narrow Italic" "Arial Narrow Bold Italic"; do
  ln -sf "/System/Library/Fonts/Supplemental/$f.ttf" "schriften/$f.ttf"
done
----

Ein anderer Ordner wird als zweites Argument übergeben; die Ausgabe bekommt dann seinen Namen
als Zusatz, z. B. `ausgabe/geschaeftsbrief-einseitig-leer.pdf`.

=== Ersatzschriften

Fehlt eine Familie im Ordner des Hosts, löst der Prototyp sie nach ADR-017 auf: Ersatzschrift
aus `ersatzschriften/zuordnung.properties`, sonst die Standardschrift. Die Ersatzschrift wird
unter dem Familiennamen der Vorlage registriert, das CSS bleibt gleich, und PDF und Vorschau
bekommen dieselbe Datei. Für jede ersetzte Familie gibt es einen Hinweis, wie ihn die
Administration zeigen würde. Die freien Schriften lädt `ersatzschriften/laden.sh` mit festen
Versionen und Prüfsummen; sie werden nicht eingecheckt.

[source,sh]
----
sh ersatzschriften/laden.sh
mkdir -p leer
../gradlew run --args="geschaeftsbrief-mehrseitig leer"
../gradlew vergleich --args="referenz/geschaeftsbrief-mehrseitig-word.pdf ausgabe/geschaeftsbrief-mehrseitig-leer.pdf"

# Laufweiten von Kandidaten gegen die Originalschrift (Dateinamen ohne Leerzeichen)
../gradlew laufweiten --args="<original.ttf> <kandidat.ttf> ..."
----

Ergebnis:

* *Arial → Liberation Sans 2.1.5* (SIL OFL 1.1): gleiche Laufweiten, wie ADR-017 annimmt.
* *Arial Narrow → PT Sans Narrow* (SIL OFL 1.1). Eine OFL-Schrift mit gleichen Laufweiten gibt
  es nicht. Gemessen an den Texten des Geschäftsbriefs, die in Arial Narrow stehen:
+
[cols="2,1,1", options="header"]
|===
| Kandidat (statisch, regulär / fett) | Mittlere Laufweite | Größte Abweichung je Text
| Encode Sans Condensed | 104,4 % / 107,5 % | 12,7 % / 19,5 %
| Fira Sans Condensed | 108,8 % / 105,8 % | 16,8 % / 13,1 %
| IBM Plex Sans Condensed | 111,3 % / 110,6 % | 16,6 % / 13,9 %
| PT Sans Narrow | 93,9 % / 92,8 % | 21,9 % / 17,0 %
|===
+
Eine breitere Schrift bricht in den Spalten fester Breite um: Mit Encode Sans Condensed läuft
die fette Zeile „(bitte Bezeichnung des Sachgebietes ergänzen)“ im Infoblock auf zwei Zeilen,
und alles darunter rückt 4,2 mm tiefer. PT Sans Narrow ist schmaler; alle Umbrüche bleiben,
die Zeilenanfänge liegen weiter höchstens 0,1 mm neben Word, und das Chrome-Druck-PDF der
Vorschau erfüllt gegen das PDF die Kriterien aus QS-004 (Teilergebnis, siehe unten). Die Texte in Arial Narrow werden dabei 6 bis 7 % kürzer, und PT Sans wirkt weicher als
Arial. Ob das Bild reicht, entscheidet die zentrale Abteilung (QS-013). Variable Schriften wie
Archivo Narrow oder Roboto Condensed sind nicht geprüft; PDFBox bettet sie nicht verlässlich ein.
* Beide Referenzschreiben bleiben mit Ersatzschriften PDF/A-2b und PDF/UA-1.
* *Ligaturen:* PDFBox 3 setzt bei PT Sans Narrow die Ligatur „fi“ und schreibt sie als
  U+FB01 („ﬁ“) in den Text des PDFs; Chrome setzt sie auch, schreibt aber „fi“. Optisch gleich.
  Wer im PDF nach „superfirma“ sucht oder den Text kopiert, bekommt je nach Viewer „superﬁrma“.
  Arial hat keine fi-Ligatur. `vergleich` normalisiert Text deshalb nach NFKC. Abhilfe fürs
  Produkt wäre, Ligaturen beim Einbetten abzuschalten oder die Ersatzschrift ohne `liga`
  auszuliefern; Letzteres ändert die Schrift und verlangt nach der OFL einen neuen Namen.
* Times New Roman und Courier New stehen in der Zuordnung, ihre Ersatzschriften sind nicht
  geladen; der Geschäftsbrief braucht sie nicht. Fehlt eine Ersatzschrift, greift die
  Standardschrift Liberation Sans mit eigenem Hinweis.

== Aufrufe

Alle Aufrufe im Ordner `prototyp/`; sie nutzen den Gradle-Wrapper des Repositorys. Die
Vorschau braucht Paged.js und Playwright aus `npm install`. Playwright nutzt das installierte
Google Chrome und lädt keinen eigenen Browser.

[source,sh]
----
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install

# Schreiben erzeugen: ausgabe/<schreiben>.html, .pdf und -vorschau.html
../gradlew run --args="geschaeftsbrief-einseitig"
../gradlew run --args="geschaeftsbrief-mehrseitig"

# Vorschau prüfen (CSP, Sandbox, Paginierung) und als ausgabe/<schreiben>-vorschau.pdf drucken,
# dann gegen das PDF vergleichen (QS-004)
npm run pruefen -- geschaeftsbrief-einseitig
npm run pruefen -- geschaeftsbrief-mehrseitig
../gradlew vergleich --args="ausgabe/geschaeftsbrief-einseitig.pdf ausgabe/geschaeftsbrief-einseitig-vorschau.pdf"
../gradlew vergleich --args="ausgabe/geschaeftsbrief-mehrseitig.pdf ausgabe/geschaeftsbrief-mehrseitig-vorschau.pdf"

# Gegenprobe: erkennt der Vergleich eine zusätzliche Seite oder Zeile?
../gradlew gegenprobe --args="ausgabe/geschaeftsbrief-mehrseitig.pdf"

# Textpositionen eines PDFs ausgeben
../gradlew positionen --args="ausgabe/geschaeftsbrief-einseitig.pdf"

# Mit dem Word-PDF der Vorgabe vergleichen
../gradlew vergleich --args="referenz/geschaeftsbrief-word.pdf ausgabe/geschaeftsbrief-einseitig.pdf"
../gradlew vergleich --args="referenz/geschaeftsbrief-mehrseitig-word.pdf ausgabe/geschaeftsbrief-mehrseitig.pdf"

# Barrierefreiheit der Vorschau (QS-003, ADR-014): axe-core, Accessibility-Baum, Tastatur, Zoom
npm run barrierefreiheit -- geschaeftsbrief-mehrseitig

# HTML-Bereinigung (ADR-014): bösartiges Testschreiben in der Vorschau angreifen lassen
../gradlew run --args="boesartig"
npm run angriff -- boesartig
# Gegenprobe ohne Bereinigung: Die CSP allein muss jeden Code blockieren
BEREINIGUNG=aus ../gradlew run --args="boesartig"
npm run angriff -- boesartig --gegenprobe

# PDF/A-2b (QS-001) und PDF/UA-1 (QS-002) mit veraPDF prüfen
../gradlew konformitaet --args="ausgabe/geschaeftsbrief-einseitig.pdf ausgabe/geschaeftsbrief-mehrseitig.pdf"

# Strukturhierarchie (Tags) mit dem Text je Element für die manuelle Stichprobe aus QS-002
../gradlew struktur --args="ausgabe/geschaeftsbrief-einseitig.pdf"

# Jede Seite als PNG ausgeben: ausgabe/<schreiben>-s<seite>.png
../gradlew bild --args="ausgabe/geschaeftsbrief-mehrseitig.pdf"
----

== Referenz-PDFs

`geschaeftsbrief-word.pdf` ist die DOCX-Vorgabe, mit Microsoft Word für macOS als PDF
gespeichert. Das Word-PDF hat eine zweite, leere Seite mit Kopfzeile; der Prototyp erzeugt sie
nicht. Der Vergleich mit Word meldet deshalb für das einseitige Schreiben ausdrücklich eine
abweichende Seitenzahl und die fehlende Zeile „Seite 2 von 2“. Das ist der einzige bekannte
Unterschied.

`geschaeftsbrief-mehrseitig-word.pdf` entsteht aus einer abgeleiteten DOCX, in der statt des
Ausfüllhinweises die Absätze aus `mehrseitig-absaetze.txt` stehen. Dieselben Absätze stehen
im Standardschreiben `mehrseitig.ftlh`.

[source,sh]
----
python3 -I referenz/mehrseitige-docx.py ../src/examples/Geschaeftsbrief.docx \
    referenz/mehrseitig-absaetze.txt /tmp/Geschaeftsbrief-mehrseitig.docx
# danach in Word öffnen und als PDF sichern
----

== Vergleich und QS-004

`vergleich` sucht zu jeder Zeile der Referenz den Partner im Kandidaten und umgekehrt. Er
meldet fehlende und überzählige Zeilen, Textabweichungen und die größte Positionsabweichung.
Dazu prüft er die Kriterien aus QS-004: gleiche Seitenzahl, gleiche erste und letzte Textzeile
je Seite, Abweichung höchstens 1 mm. Ist eines verletzt, endet er mit Status 1.

Stand, Teilergebnis von QS-004: Das Chrome-Druck-PDF der Vorschau erfüllt gegen das PDF die
Kriterien für beide Referenzschreiben, mit höchstens 0,3 mm Abweichung. Ob die
Bildschirmdarstellung der Vorschau ebenso genau ist, misst der Prototyp nicht.

`gegenprobe` macht aus einem PDF Kandidaten mit bekanntem Fehler: eine zusätzliche leere Seite,
eine angehängte Kopie der letzten Seite und eine zusätzliche Zeile am Seitenende. Alle drei
muss der Vergleich als verletzt melden, das unveränderte PDF als erfüllt. Die Gegenprobe hat
dabei einen echten Fehler gefunden: Die versteckte Kopie der Fußzeile für Screenreader
erzeugte im Chrome-Druck ein zusätzliches leeres Blatt. Sie ist im Druck jetzt ausgeblendet.

== Vorgehen bei den Maßen

Die Maße im Briefpapier stammen aus der DOCX: Seitenränder, Rahmen, Tabstopps und
Formatvorlagen. Wo Word eigene Regeln anwendet, z. B. beim Zeilenabstand, sind sie an den
Grundlinien des Word-PDFs abgeglichen. Die Kommentare im CSS nennen die Grundlinie, auf die
eine Angabe zielt. Was dabei über openhtmltopdf gelernt wurde, steht an der jeweiligen Stelle
im CSS.

== Vorschau

Das Dokument im iframe ist das HTML des PDFs mit Zusätzen im Kopf, die das Layout nicht
ändern:

* Content Security Policy: `default-src 'none'`, Skripte nur per SHA-256-Hash (Paged.js und
  seine Konfiguration), Schriften und Bilder nur als `data:`-URI. `style-src` braucht
  `'unsafe-inline'`, weil Paged.js zur Laufzeit eigene `<style>`-Elemente anlegt.
* Die Schriften des Hosts als `@font-face` mit `data:`-URIs. Das macht das Dokument rund 5 MB
  groß; im Produkt kämen sie vom Ressourcen-Endpunkt der Bibliothek.
* Eine Bildschirmdarstellung der Seiten, die nur unter `@media screen` wirkt.

Was beim Abgleich mit Paged.js 0.4.3 gelernt wurde, steht im CSS des Briefpapiers: ein
Randfeld mit `content: none` blendet die folgenden Randfelder derselben Seite aus; der Abstand
vor dem ersten Absatz einer Folgeseite bleibt erhalten; Randfelder zählen den Einzug in die
Breite.

== Konformität

`konformitaet` prüft mit der veraPDF-Bibliothek (Greenfield-Modell) gegen PDF/A-2b und
PDF/UA-1 und listet jede verletzte Regel mit Anzahl und Beispielmeldung. Die Gegenprobe mit
dem Word-PDF und dem Chrome-PDF der Vorschau, die beide nicht als PDF/A erzeugt sind, zeigt die
erwarteten Verstöße: fehlende XMP-Metadaten, kein Tagging, keine Sprachangabe.

Was veraPDF nicht prüft und die Stichprobe klären muss, zeigt `struktur`. Beim Stand dieses
Prototyps fällt auf:

* Die Fußzeile (Öffnungszeiten, Homepage) wird im PDF vorgelesen, und zwar nach dem Brieftext.
  openhtmltopdf gibt laufende Elemente (`position: running()`) grundsätzlich als
  Paginierungs-Artefakt aus; eine Einstellung dafür gibt es nicht. Als Fließinhalt der ersten
  Seite geht es auch nicht: Unterhalb des Inhaltsbereichs schiebt openhtmltopdf ein absolut
  positioniertes Element auf die nächste Seite. Deshalb schreibt `FusszeileTaggen` das fertige
  PDF nach: Artefakt-Abschnitte mit Text ganz im unteren Seitenrand werden je Textblock zu
  `/P <</MCID n>>`, und je Block hängt ein `P` am Ende des Strukturbaums. Kopfzeilen wie
  „Seite x von y“ bleiben Artefakte. Das entspricht dem im Review zu PR #47 beschlossenen und
  in QS-002 übernommenen Antwortmaß. Bei jeder Erzeugung prüft der Prototyp, dass genau die Fußzeilentexte aus dem HTML in dieser Reihenfolge am Ende des Strukturbaums stehen.
  Preis: Der Schritt hängt davon ab, wie openhtmltopdf den
  Content-Stream schreibt (Artefakt-Abschnitte, ein Textblock je Spalte), und muss bei jedem
  Update von openhtmltopdf mitgeprüft werden. Im Produkt läge er vor einer Signatur des PDFs.
* Der Betreff ist eine Überschrift (`H1`), sieht aber aus wie in der Word-Vorgabe.
* Die Anschrift (`<address>`) wird zu `Sect` mit `P`, nicht zu einem eigenen Tag.

NVDA-Stichprobe (Owner, 2026-11-23) mit NVDA 2026.1.1 und Adobe Acrobat Reader 2026.001.21662
unter Windows, an `geschaeftsbrief-einseitig.pdf` und `geschaeftsbrief-mehrseitig.pdf`:

* „Alles lesen“ (NVDA+↓) liest den Brief sauber und verständlich auf Deutsch vor.
* „Seite x von y“ wird nicht vorgelesen; es ist ein Artefakt. Beim Seitenwechsel sagt NVDA selbst
  „Seite 2“ bzw. „Seite 3“ an.
* Beim Blättern auf die dritte Seite sagt NVDA „3 Schrägstrich 3 c“ an. Vermutlich ist das die
  Seitenanzeige des Readers; im Strukturbaum steht kein solcher Text, und beim durchgehenden
  Lesen tritt es nicht auf.
* NVDA sagt den Dokumenttitel an. Die Sprache sagt NVDA nicht an; das tut es auch sonst nicht,
  es wählt damit nur die Stimme. Das PDF setzt `/Lang (de)` im Katalog und am
  `Document`-Element (`struktur`).
* Acrobat Reader erkennt die PDF/A-Konformitätsangabe und öffnet das Dokument im PDF/A-Modus.
* NVDA liest den Alternativtext des Logos vor.
* axesCheck von axes4 (Engine axesPAC, PDF/UA nach Matterhorn-Protokoll, WCAG Stufe A und AA)
  meldet für beide PDFs PDF/UA und WCAG als erfüllt (Owner, 2026-11-23). Als Titel zeigt es
  „(Bitte Betreff ergänzen)“, den Betreff des Musterbriefs. Es bleibt je eine Warnung, zu der
  axesCheck keine Details anzeigt: bei PDF/UA unter „Logical Structure“ → „Structure Tree“,
  bei WCAG unter „4 Robust“ → „4.1 Compatible“. Nicht weiter untersucht; die Desktop-Fassung
  von PAC zeigt die Einzelprüfung.

== Barrierefreiheit der Vorschau

`barrierefreiheit` prüft die Kriterien aus ADR-014, die sich automatisieren lassen. axe-core
läuft getrennt auf der Host-Seite und im Dokument des iframe; wegen der opaken Origin kann es
nicht von außen hineinsehen. Playwright wertet über das DevTools-Protokoll aus, die CSP des
iframe gilt dafür nicht. Stand für das mehrseitige Referenzschreiben:

* axe-core: keine Verstöße der Stufen serious und critical. Moderat bleibt „Inhalt außerhalb
  von Landmarks“ (Briefkopf, Anschrift, Infoblock).
* Der Betreff ist die Überschrift des Schreibens (`h1`), im Stil der übrigen Betreffzeilen.
* Paged.js klont ein Element, das über eine Seite reicht, samt Rolle. Aus `<main>` wurden so
  drei Landmarks. Das Schreiben ist deshalb ein `div` mit `role="main"`, und die Vorschau
  entfernt die Rolle an den Fortsetzungen (`[data-split-from]`).
* Paged.js setzt die Randfelder im DOM vor den Seiteninhalt. Ohne Eingriff liest VoiceOver
  zuerst die Fußzeile und dann den Brief (Owner, 2026-11-20), dazu „Seite x von y“ mitten im
  Text. Die Vorschau verbirgt deshalb alle Randfelder mit `aria-hidden` und hängt eine visuell
  versteckte Kopie der Fußzeile ans Ende. Lesereihenfolge jetzt: Briefkopf, Anschrift,
  Infoblock, Betreff, Brieftext, Fußzeile. Playwrights `ariaSnapshot` zeigt generierten
  CSS-Inhalt wie „Seite x von y“ nicht; die Prüfung kontrolliert deshalb die Randfelder direkt.
* Tastatur: Keine Fokusfalle. Die Seiten liegen in einem fokussierbaren Bereich
  (`role="region"`), der sich mit den Pfeiltasten scrollen lässt. „Aktualisieren“ behält den
  Fokus, beide Statusmeldungen kommen über die `aria-live`-Region.
* Zoom 200 %: In einem schmalen Fenster (1280 px, also 640 CSS-Pixel) ist die Seite breiter als
  das Fenster. Der Bereich scrollt dann waagerecht, mit der Maus und mit den Pfeiltasten. Die
  Seite selbst bricht nicht um; sie ist ein festes A4-Blatt (Ausnahme für zweidimensionale
  Inhalte in WCAG 1.4.10).

VoiceOver (Safari) liest das Schreiben im sandboxed iframe vollständig, sobald man den Frame
betreten hat (VO+Shift+Pfeil runter). Das gilt auch ohne Sandbox, mit `src` statt `srcdoc` und
mit `allow-same-origin`; die Isolation selbst ist also kein Hindernis. Safaris einfache
Vorlesefunktion liest dagegen nur die Host-Seite.

Zweiter VoiceOver-Durchgang nach dem Verbergen der Randfelder (Owner, 2026-11-20): Die
Reihenfolge stimmt, die Fußzeile kommt am Ende. *Bekannte Grenze:* Mit VO+Pfeil rechts endet
die Navigation am Ende der ersten Seite. Weiter geht es erst, wenn man den Frame verlässt und
wieder betritt; danach bis zum Ende. Das trat auch auf, wenn die Randfelder nicht verborgen
waren oder der scrollbare Bereich fehlte. Eine Vermutung ist, dass VoiceOver den ersten Teil
des Schreibens mit `role="main"` als Gruppe behandelt; die Fortsetzungen auf den Folgeseiten
haben die Rolle nicht. Nicht weiter untersucht; es kann auch an der Bedienung liegen.

NVDA (Owner, 2026-11-23, NVDA 2026.1.1 unter Windows) liest die Vorschau vollständig vor,
einschließlich der Alternativtexte.

== HTML-Bereinigung

`Bereinigung` bereinigt das fertig zusammengeführte Dokument mit jsoup nach einer Allowlist,
bevor PDF und Vorschau entstehen. Platzhalterwerte sind schon beim Zusammenführen escaped
(ADR-008); die Bereinigung fängt ab, was eine Vorlage selbst mitbringt oder mit `?no_esc` aus
den Daten durchlässt. Jede Entfernung wird als Befund gemeldet.

* *Elemente:* Struktur und Text eines Schreibens (Absätze, Überschriften, Listen, Tabellen,
  `img`, `a`, `address`, `header`, `footer`, `main` u. a.); im Kopf nur `title`, `meta` und
  `style`. Aktive und einbettende Elemente fliegen samt Inhalt heraus (`script`, `iframe`,
  `object`, `embed`, `svg`, `form`, `base`, `link`, `meta` außerhalb des Kopfs …). Andere
  unbekannte Elemente werden aufgelöst, ihr Text bleibt.
* *Attribute:* `class`, `id`, `lang`, `dir`, `title`, `role`, `style`, einige `aria-*`, dazu je
  Element das Nötige (`img`: `src`, `alt`; `a`: `href`; Tabellenzellen: `colspan`, `rowspan` …).
  Damit fallen alle Eventhandler weg.
* *URLs:* Links nur `http`, `https`, `mailto`, `tel` und Fragmente; Bilder nur
  `data:`-Bilder. Ein Link ohne erlaubtes Ziel wird zu Text. Steuer- und Leerzeichen werden vor
  der Prüfung entfernt (`java&#x09;script:`).
* *CSS* in `style`-Elementen und -Attributen: `@import` und `url()` außer `data:`-Bildern und
  -Schriften fallen weg; bei `expression()`, `javascript:` u. Ä. die ganze Stilangabe.
* *Ausgabe* als XHTML ohne Pretty-Print. openhtmltopdf braucht wohlgeformtes XML, und
  zusätzlicher Leerraum würde das Layout verschieben. Die Referenzschreiben ergeben 0 Befunde
  und unveränderte Messwerte.

Das Testschreiben `boesartig` bringt 25 Angriffe mit, aus der Vorlage und aus den Daten:
Skripte, Eventhandler, `javascript:`- und `data:`-Links (auch verschleiert), iframe, object,
embed, SVG, Formular, externe Bilder und CSS, `expression()`, `base`, `meta refresh` und einen
Kommentar. `npm run angriff` öffnet die Vorschau, fährt über alle Absätze, klickt alle Links und
beobachtet Konsole, Dialoge, Netzanfragen (alle abgebrochen), Navigationen des iframe und neue
Tabs. Ergebnis: nichts wird ausgeführt, nichts nachgeladen, das iframe bleibt beim Schreiben,
und der erlaubte Link öffnet einen neuen Tab. Das PDF
ist weiter PDF/A-2b und PDF/UA-1.

Die Gegenprobe ohne Bereinigung zeigt, was jede Schicht leistet:

* Die CSP allein blockiert jeden Code (25 Verstöße: Skripte, Eventhandler, externes CSS und
  Bilder).
* Gegen `<meta http-equiv="refresh">` hilft die CSP nicht: Das iframe springt auf eine fremde
  Seite und zeigt deren Inhalt an der Stelle des Schreibens. Das verhindert nur die Bereinigung.
* openhtmltopdf bricht ohne Bereinigung ab, weil Daten mit `?no_esc` kein wohlgeformtes XHTML
  ergeben. Ohne Bereinigung würde es außerdem externe Ressourcen laden.

Für das Produkt bleibt offen:

* Links in der Vorschau öffnen einen neuen Tab (Entscheidung des Owners, 2026-11-20). Ein
  Skript im iframe fängt den Klick ab und schickt das Ziel per `postMessage` an die Host-Seite;
  die prüft das Schema (`http`, `https`, `mailto`, `tel`) und öffnet es mit `noopener`. Das
  iframe selbst navigiert nicht, und die Sandbox braucht kein `allow-popups`.
* Ein erlaubter Link ohne `title` erzeugt den openhtmltopdf-Hinweis „PDF/UA – No title text
  provided for link“; veraPDF meldet keinen Verstoß. Ein Hinweis für Vorlagenautoren.
* Befunde in einer Vorlage werden nicht still bereinigt (Entscheidung des Owners, 2026-11-20).
  Beim Speichern einer Vorlage zeigt die Pflege die Befunde an und verlangt eine ausdrückliche
  Wahl: *Ablehnen* (die Autorin bereinigt selbst), *Trotzdem akzeptieren* (die Vorlage wird
  gespeichert; beim Rendern greifen Bereinigung und CSP weiterhin) oder *Bereinigen* (die
  Vorlage wird mit der automatischen Bereinigung gespeichert, soweit sie möglich ist). Betrifft
  die Epics „Briefpapier-Pflege“ und „Standardschreiben-Pflege“.
