=== Q-PO-002: Printing and target archive

Should “Drucken” (print) from the preview print the final PDF (proposal) or the
HTML preview? Is there a target archive with its own PDF/A requirements?

Clarification from the convergence check against issue #1 (2026-11-16): Can a
user print from an unsaved preview? If yes: Which artifact is printed, and does
this create a stored letter? If saving is a precondition: The flow up to
printing the stored PDF is recorded. The answer determines the actions of the
preview and is an acceptance criterion of #10. After that, the runtime view is
extended with the print flow.

Answer: Printing answered (Owner, PR #21, 2026-11-16):

* A preview cannot be printed. “Drucken” means deliberately printing the
  document.
* The “Drucken” button exists only for the finally stored letter, not in the
  preview. It uses the browser's print function with the content of the stored
  document.
* If someone prints the preview with the browser's print function, the
  application does not actively prevent it. But the application is not
  responsible for the result.

Implemented in the runtime view (“Print a Saved Letter”), in QS-003
and in ADR-004. The target archive is still open: Is there one with its own
PDF/A requirements (ADR-005)?

[[q-po-011]]
=== Q-PO-011: Lifetime of the preview and changed data

How long does a preview stay stored if the clerk does not save the
letter? And what applies if the domain data changes between preview and
saving?

State of the architecture: According to
xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007], the preview creates
a time-limited snapshot. Exactly this data state is saved, so later
data changes are not included. The expiry time is an assumption
(30 minutes). If the snapshot has expired, the library rejects saving
and requires a new preview (runtime view, error case “Snapshot Expired”).

Owner's proposal for the MVP (comment in PR #15, 2026-11-15): Data changes are
not addressed. The preview shows a notice that it is only a preview, and
offers an “Aktualisieren” (refresh) button that creates it
again. This proposal allows the stored letter to differ from the
preview if data read anew at saving is used. This
contradicts ADR-007, which renders from the snapshot of the preview.

To clarify:

. *Snapshot fidelity or permitted deviation:* Does it hold for the MVP that the
  stored letter matches the preview exactly (snapshot according to ADR-007)?
  Or may it differ because the current data is read at saving?
  In the second case,
  xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007] and QS-004
  (fidelity between preview and PDF) must be revised.
. *Notice and “Aktualisieren”:* Do they belong in the MVP in both variants?
  With a snapshot, the notice reads: The letter shows the data state at the
  time of the preview; “Aktualisieren” creates a new snapshot.
. *Expiry time:* Confirm the assumed 30 minutes or set a different
  duration.
. *Deletion:* When is an expired snapshot, or one replaced by “Aktualisieren”,
  actually deleted? Immediately on expiry, by a regular
  cleanup, or at the latest on the next access? The snapshot contains
  personal data from the host.

Answer: Answered (Owner, 2026-11-15):

* *Later stage:* The stored letter matches the preview exactly.
* *MVP:* It is enough if the final letter is saved with changed data
  and a notice informs the user about it. If it is possible without
  much effort, the MVP already reports data changes and
  forces a refresh of the preview.
* *Deletion:* An expired snapshot, or one replaced by “Aktualisieren”, is
  deleted immediately.

Architecture proposal, confirmed by the owner on 2026-11-15: Detecting
data changes is possible with little effort already in the MVP. The snapshot also
stores a hash (SHA-256) of the formatted data context. At saving, the library
asks the host for the permission again anyway. In doing so, it also reads the
data context anew and compares the hash. If it differs, nothing is
saved. The UI reports the change and requires “Aktualisieren”.
Rendering continues from the snapshot. This means the snapshot fidelity of the
later stage already applies in the MVP, and the variant “save with changed data”
is dropped. ADR-007 stays valid and is only extended with the hash comparison,
the runtime view with the error case “Data changed”.

On deletion: A snapshot replaced by “Aktualisieren” is deleted in the same step
in which the new one is created. On expiry, a cleanup deletes it at a short
interval (for example, every minute). Until then, the library treats an
expired snapshot like a non-existent one.

The expiry time is 30 minutes (Owner, 2026-11-15). After that, the preview is
deleted. Reloading creates a new preview. Implemented in
xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007] and the runtime view.

[[q-arch-003]]
=== Q-ARCH-003: Styling of the frontend components by the host application

How is it ensured that the React components look the way the
host application specifies (owner's comment in PR #15, 2026-11-15)?

The question shapes the frontend architecture and the integration contract of the
npm package (xref:adr-001-einbettbare-bibliothek[ADR-001]). It will probably
be decided as a separate ADR. Not all parts need to be settled equally early:

* *For the frontend scaffold (#13):* Only the way the package ships CSS.
  #13 plans UnoCSS. To decide is whether the package brings its own CSS
  and how it prevents this CSS from changing the host (no global reset,
  classes with their own prefix or in a CSS layer). This fits all three
  approaches below and does not block the scaffold.
* *Before the first component of the user interface:* Which of the three approaches applies.
* *Before the preview component:* How the preview is isolated. Besides
  style fidelity (QS-013), QS-003 (accessible preview, for example focus and
  screen readers across the boundary of an `iframe`) and QS-004
  (fidelity between preview and PDF, that is, the same styles and
  fonts in preview and rendering) count here.

Two areas need opposite rules:

* *User interface* (forms, lists, buttons): It should adopt the look
  of the host.
* *Letter in the preview*: It must follow the central DOCX specification (QS-013)
  and must not be changed by the host's styles. So it needs
  isolation, for example an `iframe` or Shadow DOM.

Possible approaches for the user interface:

. *Design tokens through CSS custom properties:* The library does its own styling
  (UnoCSS), but reads colors, fonts and spacing from variables that the host
  sets.
. *Unstyled components (headless):* The library provides behavior and
  accessibility; the host does all the styling itself.
. *The host's component library as a peer dependency:* The library
  imports the UI components of a specific component library. This
  binds it to exactly this library and its versions.
. *Render props (slots):* For individual building blocks, such as a
  button or input field, the library defines its own interface (which props
  it passes). The host can pass its own components for them; otherwise the
  library's default rendering applies. The library depends on no
  third-party library, only on its own interface. The price: This
  interface is part of the public contract and must stay stable. For
  passed components, the host shares responsibility for accessibility
  (QS-003).

To clarify: Which component libraries or design systems do the known
hosts use (see Q-ARCH-002)? Which approach applies?

Answer: Answered (Owner, 2026-11-15): The components bring their own
styles, which the host can override. The primary host application known so far
is a React application with UnoCSS. Design tokens through CSS custom
properties are fine for the admin UI and the display component.
Render props are interesting if the dependency stays manageable.

Architecture proposal, confirmed by the owner on 2026-11-15 and recorded as
xref:adr-013-styling-der-frontend-komponenten[ADR-013]:

* The library brings default styles, generated with UnoCSS, with its own
  class prefix and without a global reset. They sit in their own CSS layer
  (`@layer`). This gives the host's styles precedence, without `!important`.
* Colors, fonts and spacing come from CSS custom properties with their own
  prefix. The host sets them; otherwise default values apply.
* Render props are a later extension for individual building blocks, if a
  host wants to use its own components. They create no dependency on a
  third-party library.
* For the display component, tokens apply only to the controls around the
  letter, such as the notice and “Aktualisieren”. The letter itself stays
  isolated and follows only the DOCX specification (QS-013).

Isolation of the preview: `iframe` (Owner, 2026-11-15), recorded as
xref:adr-014-isolation-der-vorschau-im-iframe[ADR-014]. This answers the
question.

[[q-arch-004]]
=== Q-ARCH-004: Repeated saving of the same preview

What happens if the save request with the same snapshot ID arrives several times? This
happens with a double click, with parallel requests, or with a
retry after the response to a successful save was lost
(timeout). An unintended second letter must not be created
(convergence check against issue #1, 2026-11-16).

To clarify:

* Which response does a retry get after saving has already succeeded?
  For example, the same letter instead of an error.
* How is a retry of the same save operation distinguished from a deliberate new
  document creation?
* How do two simultaneous requests behave?

The rule is set with #5 and #10, before the persistence design (#6)
starts. It extends
xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007] and the runtime view.

Answer: Answered in principle (Owner, PR #21, 2026-11-16). Idempotency does not
depend on the snapshot ID but on a **domain key**:

* Every preview and every final document belongs to a business-driven
  situation with a domain key, for example a
  matter ID. The key is unique in the host application and will
  probably become part of the file name.
* A preview with the same domain key always returns the same
  result. If a snapshot already exists, it is delivered. Otherwise it is
  stored and delivered.
* The same applies to the final document: If it is already stored, it is
  delivered. Otherwise it is created, stored and delivered.
* The same document is never created repeatedly. A new document would have a
  new domain key.
* The host application specifies the key. For this, the SPI will probably be
  extended with a request for the unique identifier.

Behind this is a scenario that refines or extends the original
requirement: In the course of a business process of the host application, tasks
arise in which letters are generated. Process and task are
uniquely identifiable, for example as
`processName.instanceId.taskName.taskInstance`. Every process instance belongs
to a concrete case, in Camunda for example the business key.

Follow-up questions before the rule is recorded as an ADR:

. *Refresh and expiry:* According to
  xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007],
  “Aktualisieren”, an expired snapshot (30 minutes) and changed data
  create a new snapshot. Proposal: The key names the current
  snapshot at any time. These three triggers replace it under the same key. A
  mere retry returns the existing one.
. *User binding:* So far the snapshot is bound to the user. What applies
  if another user opens the same task, for example after a
  reassignment?
+
Answer (Owner, 2026-11-16): The snapshot stays bound to one user. It
must be prevented that two different users create a snapshot for the same domain
key.
. *Terms:* How do the domain key (task instance), the case
  (business key) and the existing business reference (type and ID, glossary)
  relate to each other? Is the case the reference by which the list filters (Q-PO-003)?
. *One key, one letter:* Does a task always create exactly one letter,
  or can one task generate several letters, for example for
  different recipients?
+
Answer (Owner, 2026-11-16): If several letters arise from one task,
this can still count as one case. A case is to be understood similarly to
a human task in BPMN: Someone has the task of creating a
letter. If a user is working on this task, no
other user can create it and thus this letter. The task
stays blocked until it is released again. If the letter has already been
created, another user cannot create it again. They are shown the
stored letter.
. *Deletion:* After a letter has been deleted through the `DeletionPolicy`,
  may a new one be created under the same key?
+
Answer (Owner, 2026-11-16): Yes.
. *File name:* How is the file name formed? This topic is new.
+
Answer (Owner, 2026-11-16): The host application specifies the file name. The
library ensures uniqueness: If a file with this name already exists,
it appends an incremented index at the end. After saving the
final letter, the library informs the host application about the
final file name and the technical key of the document. This lets the
host establish a relationship between business data and the document. The
host application is responsible for that.
+
Deferred (Owner, 2026-11-23, after the review of PR #74): The file name
is not part of the contract for saving in a transaction of the host
(xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]). The host
links its data through the ID of the letter. Recorded for later:
+
--
* *Separate two names:* The *storage name* is the technical key under which
  the PDF is stored. The *display name* is the name the user sees when
  downloading. Only the storage name must be unique, and only if it lives in a
  shared namespace, for example in the host's DMS (#60). The display name is
  only a suggestion to the browser when downloading.
* *Variants:*
** Specified by the host, with an incremented index on a collision (answer from
   2026-11-16 above). The assignment must be collision-free even with concurrent
   saving, without catching a constraint violation inside the host's
   transaction. The ID of the reference can contain characters
   that are not allowed in file names (#69).
** A generated name, for example the ID of the letter as a UUID: without collision
   and without invalid characters, but not readable for humans.
** A pattern per template that business users maintain with the template, for example
   `+PaymentReminder-${reference.id}-${date}.pdf+`, with the placeholder language
   (xref:adr-008-platzhaltersprache[ADR-008]) and the data context (epic #9).
--

Still open before the rule is recorded as an ADR:

* *Refresh and expiry (question 1):* Does the proposal hold that “Aktualisieren”,
  expiry and changed data replace the snapshot under the same key?
* *One key, several letters:* If one task generates several letters,
  each needs its own key; otherwise the second call delivers the first
  letter. Proposal: The host specifies a separate domain key per
  letter, for example the task instance with a suffix. Several keys can
  belong to the same case.
* *Terms (question 3):* So far the case was the business key of the process instance.
  The answer to question 4 describes it like a human task. What is the case, and
  how does it relate to the business reference (type and ID) and to the list
  (Q-PO-003)?
* *Lock and release:* Who locks the task, and what releases it again?
  Proposal: A non-expired snapshot of a user locks the key
  for other users. The lock ends with saving, with expiry after
  30 minutes, or with an explicit cancellation. Alternatively, the host takes over the
  lock, for example through the claim of a human task in the process engine.
* *Notification of the host:* What applies if the notification about
  file name and technical key fails? Proposal: The letter stays
  stored, and the notification is retried. Alternatively, it runs in
  the same transaction, and an error prevents saving. Both
  at once is not possible, see “Atomic or decoupled” below.
* *Saving in a transaction of the host:* The host must be able to execute saving
  atomically together with its own database actions, for example with
  completing a human task. Today it triggers saving only through the
  React components and REST. The preview stays there, because what is saved is
  the snapshot the user has seen (ADR-007).
+
Tendency (Owner, 2026-11-22, refined in the review of PR #70): The library
offers both. The two paths meet different integration needs:
+
--
.. *Java API, the primary path:* The host orchestrates in its own
   use case. It saves the letter, evaluates the result, changes
   its own data or completes the task, and commits everything together. It
   calls the API and does not implement an SPI. As ADR-016 foresees as an
   extension path, this is a separate API module with its own types
   and inbound adapter, without public coupling to the domain model or
   to the internal use case ports. REST and the Java API use the same
   use case.
.. *Optional synchronous callback:* If the user saves through the library's
   endpoint, the callback includes actions of the host. It runs after the
   library's database changes, but before the shared commit. A
   listener after the commit (`AFTER_COMMIT`) cannot provide the required
   atomicity. The callback must not repeat what a caller of the
   Java API has already done itself.
--
+
*Responsibility boundary* (Owner, in the review of PR #70):
+
--
* *The library* is responsible for its own idempotency according to ADR-021, that is,
  at most one letter per snapshot. In the contract of the API and the callback, it
  guarantees when the callback runs (on a new creation and/or on
  `AlreadySaved`), which stable identifiers it receives, that it runs before
  the shared commit, and how errors of the callback affect the shared
  transaction.
* *The host* is responsible for the idempotency of its own business actions, the
  interplay of its orchestration with a configured callback, and
  retry, recovery and, where needed, compensation of external
  side effects, for example when completing a task in a remote engine
  or when storing in its own DMS. Outbox and compensation are possible
  patterns of the host, not a requirement and not a task of the library. The
  library takes on no general workflow or compensation control.
* Idempotent saving by the library explicitly does not
  guarantee that the host's whole use case is idempotent.
* The library's guarantees belong in the API and SPI contract; the
  host's obligations, including integration examples, belong in the
  documentation on host integration. Technical limits of the respective store
  stay part of the store contract (#60).
--
+
Open on this:
+
--
* *Transaction context:* The library must join a running transaction
  (Spring `REQUIRED`, never `REQUIRES_NEW`). For the local atomic
  variant, host, library and, where present, an embedded engine must
  share the same physical transaction. A shared data source alone is
  not enough: Without a suitably integrated transaction manager, the engine
  may already have committed when the host rolls back. The library stays
  usable for hosts without a process engine.
* *Errors of the callback:* Which errors roll back the shared transaction?
  Checked exceptions and business errors as a return value do not do this
  automatically; the contract must define it.
* *Atomic or decoupled* (clarification, reviewed by the owner, 2026-11-23):
  For the notification after saving, two semantics exclude each other.
  A callback cannot provide both.
+
[horizontal]
Atomic:: The callback runs before the shared commit. If an action of the
  host fails, the letter, the consumption of the snapshot and the host's data roll back
  together. There is no retry inside the transaction, because after
  the error it is only marked for rollback (Spring: rollback-only).
  The retry is a new save attempt by the user while the
  snapshot is valid.
Decoupled:: The notification runs after the commit (`AFTER_COMMIT` or
  outbox). The letter stays stored even if the host's action
  fails. Then someone must retry the notification, and the host
  must process it idempotently. This matches the proposal under
  “Notification of the host”, but is not atomic.
+
The path through the Java API needs no callback: The host is already in
its own use case, receives the result as a return value and continues in
the same transaction. A callback concerns only saving through the
library's endpoint, where no use case of the host is running.
+
The tendency from 2026-11-22 requires atomicity and so contradicts the
proposal under “Notification of the host”. To decide is what applies to
saving through the UI: only atomic, only decoupled, or both with
a choice by the host per callback. In the decoupled case it is also open who
retries. According to the responsibility boundary above, the library takes on no
workflow control, so an outbox would be the host's business.
+
.Recommendation (proposal, 2026-11-23, accepted by the owner on the same day)
====
The library offers only the atomic callback, no notification of its own
after the commit and no retry of its own.

* This meets the tendency from 2026-11-22 and fits the responsibility boundary:
  The library only guarantees that the callback runs before the shared commit
  and that an error rolls everything back.
* If the host needs a decoupled effect, for example completing a task in
  a remote engine or storing in its own DMS, it writes an outbox job
  into the same transaction in the callback and then executes it itself
  in a retryable way. The outbox job is thus created exactly when
  the letter is stored too.
* If the recommendation is followed, the proposal under “Notification
  of the host” that the library retries the notification is dropped. An error in the callback prevents
  saving, and the user saves again.
* A choice between both semantics per callback enlarges the contract and the
  test matrix, without enabling anything that the host does not already
  achieve itself with the outbox.
====
+
Answer (Owner, 2026-11-23): The recommendation is followed. The contract is in
xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023], accepted on
2026-11-23:
+
--
* For saving through the UI there is only the atomic callback. This
  drops the proposal under “Notification of the host”: The library
  retries nothing; an error in the callback prevents saving.
* The callback runs only if the letter is created in this transaction. On
  `AlreadySaved` it does not run again.
* The callback rejects on business grounds through a sealed result with a reason for the
  user. A rejection rolls back the shared transaction, as does
  any exception.
--

* *Scope of atomicity:* Metadata of the letter, consumption of the snapshot and
  transactional data of the host commit or roll back together. An
  external store (#60) does not take part in this automatically. An orphaned
  document can therefore be created even if saving returns successfully
  and the host rolls back afterwards. The error path from ADR-021 becomes
  wider; how often it occurs is unknown. #60 needs an explicit
  path to recovery or cleanup.
* *Prepare and commit:* Rendering and the conformance check lengthen
  the host's transaction. They should preferably happen before a short
  write transaction. A prepared PDF then stays bound on the server side to
  exactly the snapshot and its checksum. At commit, the
  owner, permission, expiry, current data context and the atomic
  state change are still checked; otherwise a gap to the fidelity of the
  snapshot opens. Today's use case `SaveLetterService` renders and checks
  only at saving; this would be a deliberate restructuring.
* *Remote engine:* The library gets no dependency on a process
  engine. The host can write an outbox job in the same local transaction
  and execute the remote call in a retryable way. Idempotency
  prevents a double effect, but on its own does not guarantee that the
  second step is executed at all after a crash.
* Permission (`ForCreation`) and idempotency (ADR-021) apply equally to both
  paths.
* *Before implementation*, the concrete contract for API and transaction is needed,
  as well as integration evidence for the shared commit, a late rollback
  of the host, errors of the callback and a lost response with retry.
