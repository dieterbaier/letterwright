== ADR-024: Sprache der Ubiquitous Language im Code

=== Status

Vorgeschlagen (proposed).

Der ADR ist KI-gestützt formuliert. Er gilt erst als Architektur, wenn der Owner
ihn angenommen hat. Die offenen Fragen unten muss der Owner vor der Annahme
beantworten.

=== Entscheidung

Wir schlagen vor, die Bezeichner im Code auf Englisch umzustellen und die
Ubiquitous Language über das Glossar zweisprachig zu führen (Option 2).

* *Englisch im Code:* Typen, Methoden, Felder, Pakete, Module und Javadoc sind
  englisch, ebenso die Typen und Komponenten des Frontends. Für Umlaute gibt es
  dann keine Umschreibung mehr wie `Rueckrufergebnis` oder `Loeschanfrage`.
* *Das Glossar bleibt die Quelle der Ubiquitous Language:* Es definiert die Begriffe
  weiter auf Deutsch. Die Spalte „Im Code“ nennt verbindlich den englischen
  Bezeichner. Für jeden Fachbegriff gibt es genau einen englischen Begriff. Ein
  Synonym im Code ist ein Fehler, wie heute auch.
* *Gherkin-Features englisch:* Die Features sind ausführbare Spezifikation des
  Codes und nutzen dieselben Begriffe wie er. `# language: de` entfällt.
* *README und Integrationsdoku englisch:* Sie richten sich an Host-Entwickler
  (#11). Das README sagt deutlich, dass die Basissprache der Fachdomäne Deutsch
  ist, dass das Glossar die Begriffe deutsch definiert und dass die englischen
  Begriffe Übersetzungen sind, die teils holpern.
* *Deutsch bleibt die Architekturdokumentation:* arc42-Kapitel, ADRs,
  Qualitätsszenarien, Risiken und Glossar bleiben deutsch. Texte der Oberfläche sind
  keine Bezeichner und nicht Gegenstand dieses ADR.
* *Projekt, Paket und Artefakte heißen `letterwright`* (siehe unten).
* *Ein Zug, vor dem ersten Release:* Die Umstellung ist eine eigene Migration in
  einem Issue. Sie läuft vor dem Rest von #10, bevor weitere öffentliche Typen
  hinzukommen. Solange es kein Release gibt, bricht sie keinen Host.
* *Was RB-12 dann regelt:* Die Randbedingung gilt nur noch für die
  Architekturdokumentation. Für Code, Features, README und Integrationsdoku gilt
  dieser ADR.

==== Name von Projekt, Paket und Artefakten

Der Name `standardschreiben` ist an den deutschen Fachbegriff gebunden und folgt
nicht mehr der Sprache des Codes. Der neue Name ist *Letterwright*:

* Gebildet wie _playwright_ oder _shipwright_: jemand, der Briefe fertigt. Die
  Bibliothek fertigt aus Briefpapier, Standardschreiben und Daten des Hosts ein
  Schreiben.
* Am 2026-11-26 gab es weder ein npm-Paket noch ein GitHub-Repository dieses
  Namens. Der Owner hat den Namen am selben Tag geprüft und festgelegt.
* Daraus folgen die Gruppe `io.github.dieterbaier.letterwright`, das Paket
  `dieterbaier.letterwright`, das Gradle-Projekt `letterwright` und das npm-Paket
  `@dieterbaier/letterwright`.

Betrachtete Alternativen: `letterkit` (ein Baukasten aus Starter und Komponenten;
ein gleichnamiges GitHub-Repository existiert), `letterforge` (mehrere
gleichnamige Projekte) und ein beschreibender Name wie `letter-templates` (eindeutig,
aber kaum als Eigenname tauglich).

=== Kontext

Issue #1 hat in Frage 2 zwei Optionen genannt: Code und Ubiquitous Language im Code
englisch mit einem Glossar DE↔EN oder alles deutsch. Der Owner hat sich damals für
Deutsch entschieden. Daraus wurde RB-12, auf dem ADR-018 („Die Namen im Code sind
die Begriffe des Glossars“) und die Lösungsstrategie (Code-Stil) aufbauen.

Seitdem hat sich die Lage geändert:

* *Der Vertrag mit dem Host ist öffentlich.* Die Module `spi` (ADR-016) und `api`
  (ADR-023) sind die einzigen Teile der Bibliothek, gegen die der Host kompiliert.
  Ihre Namen und ihre Javadoc liest jedes Entwicklerteam, das die Bibliothek
  einbindet. Heute heißen sie zum Beispiel `PlatzhalterdatenAnbieter`,
  `NachDemSpeichern`, `Rueckrufergebnis` und `Loeschentscheidung`.
* *Die Bibliothek ist Open Source (MIT, RB-07).* Wer beitragen will, liest den
  Kern. Deutsche Namen neben englischer Java- und Spring-API und Umschreibungen
  wie `ue` erschweren das auch für Deutschsprachige.
* *Es gibt noch kein Release.* Eine Umbenennung kostet heute Arbeit, nach dem
  ersten Release bricht sie die API des Hosts. Jedes weitere Issue mit öffentlichen
  Typen macht sie teurer.

Der Bestand bei Erstellung dieses Entwurfs, auf `main` bei `5f3ae6b`: etwa 250
Java-Dateien in 16 Gradle-Modulen mit teils deutschen Modulnamen (`domaene-*`,
`adapter-persistenz-jdbc`, `architekturtests`, `host-vertragstest`), das Paket
`dieterbaier.standardschreiben`, zehn Gherkin-Dateien mit `# language: de` und das
npm-Paket `komponenten`. Das Datenbankschema mit Liquibase (#6) gibt es noch nicht.
Die Zahlen liefert zum Beispiel `find src/application -name '*.java' | wc -l`.

Die Fachsprache selbst ist deutsch und an deutsche Normen gebunden (DIN 5008,
Form A und B). Für manche Begriffe gibt es kein eindeutiges englisches Wort, allen
voran „Standardschreiben“.

=== Entscheidungstreiber

* **Zugänglichkeit des Vertrags:** Host-Entwickler und Beitragende ohne
  Deutschkenntnisse verstehen SPI, Java-API und Kern.
* **Nähe zur Fachsprache:** Das Gespräch mit Fachanwendern und die Gherkin-Szenarien
  nutzen ihre Begriffe ohne Übersetzung.
* **Eine Sprache im Code:** keine Mischung mit der englischen Java- und
  Spring-API, keine Umschreibung von Umlauten.
* **Eine Sprache im Modell:** Ein Fachbegriff hat im Code genau einen Namen. An der
  Grenze zum Host wird nicht übersetzt.
* **Aufwand der Umstellung:** Code, Tests, Features, Doku und Glossar.

=== Betrachtete Optionen

==== Option 1: Alles bleibt deutsch (Status quo, RB-12)

Code, Glossar und Dokumentation bleiben deutsch. Es gibt keinen Aufwand und keine
Übersetzung. Der öffentliche Vertrag bleibt für alle schwer lesbar, die kein Deutsch
sprechen.

==== Option 2: Code englisch, Glossar DE↔EN, Architekturdoku deutsch (vorgeschlagen)

Wie oben beschrieben. Code und Features stehen in einer Sprache, README und
Integrationsdoku sprechen Host-Entwickler auf Englisch an, und das Glossar ist die
verbindliche Brücke zur deutschen Fachsprache. Die Umstellung kostet einmal Arbeit.
Wer mit Fachanwendern spricht, muss die Zuordnung im Glossar kennen.

==== Option 3: Nur SPI und Java-API englisch, innen deutsch

Der Host sieht englische Namen, der Kern bleibt deutsch. Der Adapter an der Grenze
übersetzt zwischen beiden Sprachen. Jeder Begriff hat dann zwei Namen im Code. Das
widerspricht der Ubiquitous Language mehr als jede einheitliche Lösung, und für
Beitragende ändert sich nichts.

==== Option 4: Alles englisch, auch die Dokumentation

Wie Option 2, dazu Architekturdokumentation, ADRs und Glossar auf Englisch. Das wäre am
zugänglichsten, entfernt die Doku aber von den Fachanwendern und verlangt die
Übersetzung aller 23 ADRs und der arc42-Kapitel.

=== Pugh-Matrix

`+1` steht für bessere Unterstützung, `0` für neutral und `-1` für schwächere
Unterstützung. Die Matrix ist ungewichtet.

[.pugh-matrix]
[cols="2,1,1,1,1", options="header"]
|===
| Kriterium | Option 1 | Option 2 | Option 3 | Option 4
| Zugänglichkeit des Vertrags | -1 | +1 | +1 | +1
| Nähe zur Fachsprache | +1 | 0 | 0 | -1
| Eine Sprache im Code | -1 | +1 | -1 | +1
| Eine Sprache im Modell | +1 | +1 | -1 | +1
| Aufwand der Umstellung | +1 | -1 | 0 | -1
s| Summe s| +1 s| +2 s| -1 s| +1
|===

Option 2 bekommt bei der Nähe zur Fachsprache `0`, weil Glossar,
Architekturdoku und Gespräch deutsch bleiben, Code und Features aber nicht. Option 3 bekommt bei der
Zugänglichkeit `+1`, weil Hosts nur den Vertrag sehen. Für Beitragende bliebe der
Kern trotzdem deutsch. Beim Aufwand bekommt Option 3 `0`, weil zwar nur der
Vertrag umbenannt wird, aber eine dauerhafte Übersetzungsschicht hinzukommt.

=== Konsequenzen

==== Positiv

* SPI, Java-API und Javadoc sind ohne Deutschkenntnisse lesbar. Das hilft bei der
  Integration (QS-007) und bei Beiträgen.
* Im Code steht eine Sprache, ohne Umschreibung von Umlauten.
* Geschieht die Umstellung vor dem ersten Release, bricht sie keinen Host.

==== Negativ

* Einmaliger Aufwand: Typen, Pakete, Module, Tests, Gherkin-Steps, Frontend,
  Glossar, Bausteinsicht und alle ADRs, die Bezeichner im Code nennen. Die ADR-Texte
  selbst bleiben deutsch, ihre Code-Beispiele ändern sich.
* Bis zur Migration laufen Issues mit deutschen Namen weiter, oder sie warten.
  Beides kostet.
* Fachbegriffe und Bezeichner unterscheiden sich. Wer zwischen Gespräch und Code
  wechselt, braucht das Glossar. Das gilt auch für die Features: Ein Fachanwender
  liest sie nicht mehr in seiner Sprache.
* Der Name des Projekts ändert sich. Links, Pages-URL und Verweise in Issues
  zeigen auf den alten Namen, bis das Repository umbenannt ist.
* Eine schlechte Übersetzung eines Kernbegriffs prägt den Code dauerhaft. Sie ist
  später so teuer zu ändern wie jetzt die Umstellung.

==== Neutral oder Folgearbeiten

* Ein Issue für die Migration, vor dem Rest von #10, mit Reihenfolge: Glossar mit
  englischen Begriffen, Kern, SPI/API, Adapter, Starter, Frontend, Features,
  Gruppe, Paket und Artefakte, README und Integrationsdoku.
* Das Glossar bekommt eine Spalte für den englischen Begriff oder führt ihn in der
  Spalte „Im Code“. Das entscheidet die Migration.
* RB-12 nach der Annahme anpassen: „Architekturdokumentation auf Deutsch;
  Bezeichner im Code, Features, README und Integrationsdoku englisch nach
  ADR-024“. Bis dahin verweist RB-12 auf diesen ADR.
* Das GitHub-Repository umbenennen. GitHub leitet alte URLs weiter; die
  Pages-URL und der lokale Ordner ändern sich. Das entscheidet der Owner mit der
  Migration.
* ADR-018 und die Lösungsstrategie (Code-Stil) verweisen auf diesen ADR.
* Die Commit-Messages sind schon englisch. Für sie ändert sich nichts.

=== Annahmen

* Bis zur Migration gibt es kein Release, und kein Host außerhalb des Projekts
  kompiliert gegen `spi` oder `api`.
* Die Zielgruppe der Bibliothek ist nicht auf deutschsprachige Entwicklerteams
  beschränkt, auch wenn die Fachdomäne deutsch ist.
