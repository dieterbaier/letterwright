== ADR-024: Language of code, ubiquitous language and documentation

=== Status

Accepted on 2026-11-26.

The ADR was drafted with AI support. Option 2 was proposed: code in English,
architecture documentation in German. The owner accepted the ADR on 2026-11-26,
but with option 4: architecture documentation and ADRs are in English as well,
and the domain glossary is bilingual. His reason: whoever wants to contribute
to development must understand the architecture documentation. German
documentation excludes everyone who does not speak German; English is common
and accepted in IT. Before that, he had answered the five open questions of the
first draft and fixed the name `letterwright`.

=== Decision

Code and documentation of the project are in English. The German domain
language is preserved through a bilingual glossary (option 4).

* *English in the code:* Types, methods, fields, packages, modules and Javadoc
  are in English, as are the types and components of the frontend. There is
  then no longer any transcription of umlauts such as `Rueckrufergebnis` or
  `Loeschanfrage`.
* *Gherkin features in English:* The features are an executable specification
  of the code and use the same terms as the code. `# language: de` is dropped.
* *Architecture documentation in English:* arc42 chapters, ADRs, quality
  scenarios, risks, questions and answers as well as vision and roadmap are in
  English. Artifact IDs, anchors and file names stay stable, even if they
  contain German words.
* *README and integration documentation in English:* They address host
  developers (#11). The README states clearly that the base language of the
  business domain is German, that the glossary names the German terms and that
  the English terms are translations, some of them clumsy.
* *Bilingual domain glossary:* For every domain term, the glossary names the
  German term of the domain language and, as binding, the English term in the
  code. For every domain term there is exactly one English term. A synonym in
  the code is an error, as it is today. The definitions are in English like
  the rest of the documentation.
* *User interface texts* are not identifiers and not the subject of this ADR.
* *Project, package and artifacts are named `letterwright`* (see below).
* *Two steps:*
** The code is migrated in one go in a separate issue, before the rest of #10
   and before further public types are added. As long as there is no release,
   this breaks no host. This migration adjusts the identifiers in the still
   German documentation.
** The AI translates the architecture documentation in a separate docs PR. The
   owner reviews the translation separately. Until this PR is merged, new
   architecture documentation continues to be written in German, so that the
   documentation is not half translated.
* *RB-12 is dropped:* The constraint “Documentation and ubiquitous language in
  German” no longer applies. This ADR takes its place.

==== Name of Project, Package and Artifacts

The name `standardschreiben` is tied to the German domain term and no longer
follows the language of the code. The new name is *Letterwright*:

* Formed like _playwright_ or _shipwright_: someone who crafts letters. The
  library crafts a letter from letterhead, letter template and data of the
  host.
* On 2026-11-26 there was neither an npm package nor a GitHub repository of
  this name. The owner checked and fixed the name on the same day.
* From this follow the group `io.github.dieterbaier.letterwright`, the package
  `dieterbaier.letterwright`, the Gradle project `letterwright` and the npm
  package `@dieterbaier/letterwright`.

Considered alternatives: `letterkit` (a construction kit of starter and
components; a GitHub repository of the same name exists), `letterforge`
(several projects of the same name) and a descriptive name such as
`letter-templates` (unambiguous, but hardly usable as a proper name).

=== Context

Issue #1 named two options in question 2: code and ubiquitous language in the
code in English with a glossary DE↔EN, or everything in German. The owner
decided for German at the time. This became RB-12, on which ADR-018 (“The names
in the code are the terms of the glossary”) and the solution strategy (code
style) build.

Since then the situation has changed:

* *The contract with the host is public.* The modules `spi` (ADR-016) and `api`
  (ADR-023) are the only parts of the library that the host compiles against.
  Every developer team that integrates the library reads their names and their
  Javadoc. Today they are named, for example, `PlatzhalterdatenAnbieter`,
  `NachDemSpeichern`, `Rueckrufergebnis` and `Loeschentscheidung`.
* *The library is open source (MIT, RB-07).* Whoever wants to contribute reads
  the core. German names next to the English Java and Spring API, and
  transcriptions such as `ue`, make this harder even for German speakers.
* *There is no release yet.* A rename costs work today; after the first
  release it breaks the host's API. Every further issue with public types
  makes it more expensive.

The code base when this draft was written, on `main` at `5f3ae6b`: about 250
Java files in 16 Gradle modules, some with German module names (`domaene-*`,
`adapter-persistenz-jdbc`, `architekturtests`, `host-vertragstest`), the package
`dieterbaier.standardschreiben`, ten Gherkin files with `# language: de` and
the npm package `komponenten`. The database schema with Liquibase (#6) does not
exist yet. The numbers come, for example, from
`find src/application -name '*.java' | wc -l`.

The domain language itself is German and tied to German standards (DIN 5008,
form A and B). For some terms there is no unambiguous English word, above all
“Standardschreiben”.

=== Decision Drivers

* **Accessibility of the contract:** Host developers and contributors without
  knowledge of German understand the SPI, the Java API and the core.
* **Closeness to the domain language:** The conversation with domain users and
  the Gherkin scenarios use their terms without translation.
* **One language in the code:** no mix with the English Java and Spring API,
  no transcription of umlauts.
* **One language in the model:** A domain term has exactly one name in the
  code. There is no translation at the boundary to the host.
* **Accessibility of the architecture documentation:** Co-developers without
  knowledge of German understand decisions, quality goals and building blocks.
* **Effort of the migration:** code, tests, features, documentation and
  glossary.

=== Considered Options

==== Option 1: Everything stays German (status quo, RB-12)

Code, glossary and documentation stay German. There is no effort and no
translation. The public contract stays hard to read for everyone who does not
speak German.

==== Option 2: Code in English, glossary DE↔EN, architecture documentation in German

As described above. Code and features are in one language, README and
integration documentation address host developers in English, and the glossary
is the binding bridge to the German domain language. The migration costs work
once. Whoever talks with domain users must know the mapping in the glossary.

==== Option 3: Only SPI and Java API in English, German inside

The host sees English names, the core stays German. The adapter at the
boundary translates between both languages. Every term then has two names in
the code. This contradicts the ubiquitous language more than any uniform
solution, and nothing changes for contributors.

==== Option 4: Everything in English, domain glossary bilingual (chosen)

Like option 2, plus architecture documentation and ADRs in English. The
glossary names German and English terms. This is the most accessible, but
moves the documentation away from German-speaking domain users and requires
the translation of all ADRs and arc42 chapters.

=== Pugh Matrix

`+1` stands for better support, `0` for neutral and `-1` for weaker support.
The matrix is unweighted.

[.pugh-matrix]
[cols="2,1,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3 | Option 4
| Accessibility of the contract | -1 | +1 | +1 | +1
| Closeness to the domain language | +1 | 0 | 0 | -1
| One language in the code | -1 | +1 | -1 | +1
| One language in the model | +1 | +1 | -1 | +1
| Accessibility of the architecture documentation | -1 | -1 | -1 | +1
| Effort of the migration | +1 | -1 | 0 | -1
s| Total s| 0 s| +1 s| -2 s| +2
|===

Option 2 gets `0` for closeness to the domain language, because glossary,
architecture documentation and conversation stay German, but code and features
do not. Option 3 gets `+1` for accessibility, because hosts only see the
contract. For contributors, the core would still stay German. For the effort,
option 3 gets `0`, because only the contract is renamed, but a permanent
translation layer is added.

The first draft did not have the criterion “Accessibility of the architecture
documentation” and therefore proposed option 2. The owner introduced it at the
acceptance. Option 4 stays at `-1` for closeness to the domain language: the
bilingual glossary softens the distance, but a domain user still does not read
the documentation in their language.

=== Consequences

==== Positive

* SPI, Java API, Javadoc and architecture documentation are readable without
  knowledge of German. This helps with integration (QS-007) and with
  contributions.
* The code is in one language, without transcription of umlauts.
* If the migration happens before the first release, it breaks no host.

==== Negative

* One-time effort: types, packages, modules, tests, Gherkin steps, frontend,
  glossary, building block view and all ADRs that name identifiers in the code.
* The translation of the entire architecture documentation costs a separate PR
  and a separate review by the owner. Until then, the documentation is German
  and the code English.
* Until the migration, issues with German names continue, or they wait. Both
  cost.
* Domain terms and identifiers differ. Whoever switches between conversation
  and code needs the glossary. This also applies to the features: a domain user
  no longer reads them in their language, nor the architecture documentation.
* The name of the project changes. Links, the Pages URL and references in
  issues point to the old name until the repository is renamed.
* A bad translation of a core term shapes the code permanently. Changing it
  later is as expensive as the migration is now.

==== Neutral or Follow-Up

* #84: Migration of the code, before the rest of #10, in this order:
  glossary with English terms, core, SPI/API, adapters, starter, frontend,
  features, group, package and artifacts, README and integration
  documentation.
* #85: Translation of the architecture documentation in a separate docs PR,
  reviewed separately by the owner.
* The glossary gets a column for the English term or lists it in the column
  “In code”. The migration decides this.
* RB-12 is removed with the acceptance of this ADR. `AGENTS.md` describes the
  language rule according to this ADR.
* Rename the GitHub repository. GitHub redirects old URLs; the Pages URL and
  the local folder change. The owner decides this with the migration.
* ADR-018 and the solution strategy (code style) refer to this ADR.
* The commit messages are already in English. Nothing changes for them.

=== Assumptions

* Until the migration there is no release, and no host outside the project
  compiles against `spi` or `api`.
* The target audience of the library is not limited to German-speaking
  developer teams, even if the business domain is German.

=== Open Questions

* None. The owner fixed the name `letterwright` on 2026-11-26 and answered the
  five questions of the first draft on the same day: Gherkin in English; README
  and integration documentation in English with a note on German as the base
  language; `LetterTemplate` and `BusinessReference`; package and artifact are
  renamed; migration before the rest of #10.
