[[adr-005-pdfa-und-barrierefreiheit]]
== ADR-005: PDF/A, PDF/UA and WCAG target level

=== Status

Proposed.

This ADR was created with AI assistance. It counts as an architecture decision
only once the responsible owner has reviewed and accepted it.

=== Decision

We propose:

* Saved letters are **PDF/A-2b** (archivability, the simplest common level
  with support for transparency and OpenType) **and PDF/UA-1** (tagged,
  accessible PDF). PDF/A-2b plus PDF/UA-1 covers in content what PDF/A-2a
  would additionally require.
* The HTML preview meets **WCAG 2.1 Level AA**, the basis of EN 301 549 and
  BITV 2.0.
* The **build checks** both automatically: **veraPDF** (open source) validates
  every reference PDF against PDF/A-2b and PDF/UA-1, **axe-core** checks the
  rendered preview in component tests and E2E tests.
* At runtime, a conformance check runs through the port `ConformanceChecker`
  **before every save**. The starter **requires a checker**:
** The default is a veraPDF adapter (veraPDF can be used under MPL 2.0 and is
   thus compatible with MIT), which the starter ships and configures
   automatically.
** **No checker configured**: the application context does not start (fail-fast
   with a clear error message). Switching it off is not intended.
** **Check fails** (not conformant): nothing is persisted; the user receives a
   message (fail-closed).
** **Check cannot be run** (error, timeout): as for “not conformant”, nothing
   is persisted. A retry is possible.
* In addition, when a **template version is published**, a proof PDF with
  sample data is created and checked, so that errors from newly maintained
  templates show up before the first save. The reference cases in CI only
  safeguard the library, not every maintained template.

=== Context

The owner gave no specific requirement: start with the simplest level, but
check it in the build. Accessibility applies to the preview and to the saved
document. Only level “a” of PDF/A or additional PDF/UA ensures tagged PDF;
PDF/A-2b alone would not be accessible.

=== Decision Drivers

* The simplest level that meets archiving and accessibility at the same time.
* Automatically checkable with open source tools.
* Supported by the rendering library.

=== Considered Options

==== Option 1: PDF/A-2b plus PDF/UA-1, WCAG 2.1 AA

A common combination, supported by openhtmltopdf, checkable by veraPDF.

==== Option 2: PDF/A-2b only

The simplest, but not accessible without tagging. Does not meet the
requirement from the issue.

==== Option 3: PDF/A-3a plus PDF/UA-2, WCAG 2.2 AA

The highest level, allows embedded files. More effort, less tool support for
PDF/UA-2.

=== Pugh Matrix

`+1` stands for better support, `0` for neutral, `-1` for weaker support and
`?` for a rating that needs human review or a prototype. If a column contains a
`?`, its sum is `?` as well.

=== Consequences

==== Positive

* Conformance is measurable in CI and safe against regressions.
* The way to higher levels stays open.

==== Negative

* veraPDF as a mandatory runtime check enlarges the host artifact and makes
  saving take longer (feeds into QS-012).
* A failure of the check prevents saving; this is intended (fail-closed).
* Content from business users (alternative texts, headings) affects conformance (R-005).

==== Neutral or Follow-Up

* veraPDF integration in Gradle/CI in the first build epic.


=== Result of the prototype

The throwaway prototype from #3 (`prototyp/README.adoc`) uses openhtmltopdf to
create PDF/A-2b with PDF/UA-1 tagging and checks it with the veraPDF library
(`validation-model`, Greenfield model) in the JVM:

* Both reference letters and the malicious test letter have no violations
  against PDF/A-2b and PDF/UA-1, also with substitute fonts. The cross-check
  with the Word PDF and the Chrome PDF of the preview shows the expected
  violations.
* A link without `title` produces a notice from openhtmltopdf, but no veraPDF
  violation. This is a hint for template authors.
* What veraPDF does not check is shown by a structure tree with the text per
  element. It is the basis of the manual spot check from QS-002, which is still
  pending.
* Headers and footers: the content footer is read out once after the letter
  text; page numbers and repetitions stay artifacts (owner, QS-002). This
  needs a post-processing step with PDFBox
  (xref:adr-004-rendering-pipeline-fuer-vorschau-und-pdf[ADR-004]).

This shows the prerequisite from the Review Notes: generation with
openhtmltopdf and checking with veraPDF. The prototype did not measure how long
the check takes on saving (QS-012).
