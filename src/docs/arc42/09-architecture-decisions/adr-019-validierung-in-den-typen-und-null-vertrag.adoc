[[adr-019-validierung-in-den-typen-und-null-vertrag]]
== ADR-019: Where validation happens and how the null contract is enforced

=== Status

Accepted on 2026-11-22.

The owner set the direction on 2026-11-22: “The types should validate. Use
cases don’t need to.” The ADR was worded with AI assistance; the owner accepted
it and its four relations on the same day in the review of PR #62.

=== Decision

* **Only the types validate.** Value objects, aggregates, entities and the data
  types of the SPI check their required attributes in the constructor or in the
  factory method (as in
  xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018]).
  Use cases, ports, adapters and query methods do not check their parameters.
* **Illegal states cannot be represented.** What a type can express, nobody
  checks at runtime and no Javadoc explains. Instead of a flag or an optional
  field, there are separate types. First example: `TemplateAction` and
  `LetterAction` instead of `Aktion` with `brauchtBezug`, and in the SPI the
  `AuthorizationRequest` as a sealed type with `ForTemplates` and `ForLetter`.
* **Null contract at compile time.** Every package is `@NullMarked` (JSpecify).
  NullAway checks this when compiling the production code in JSpecify mode, so
  it also checks the nullability of type arguments; a violation aborts the
  build. `RequireExplicitNullMarking` allows no class without marking, so that a
  new package does not silently bypass the gate. Tests are exempt, because they
  pass `null` on purpose to check the self-validation of the types.
* **Proof that the gate works.** The task `checkNullContract` in the module
  `architecture-tests` compiles small probes with exactly the arguments of the
  production code: an unmarked class, a `null` return and a nullable type
  argument must fail, a correct class must compile. It is part of `check`.
* **Optional results.** No return value is `null`. A result that may be absent
  is an `Optional`. `Optional` is not a field and not a parameter.
* **The promise applies at the boundaries.** The promise from ADR-018 “never a
  `NullPointerException`” applies at the boundaries: when a type is created and
  for values that the host supplies. If an SPI implementation returns `null`,
  `adapter-host` still reports `HostContractViolated`. Whoever uses an internal
  signature incorrectly gets a `NullPointerException`.
* **What NullAway does not guarantee.** NullAway is a static analysis and
  prevents most such errors in production code, but not every one. Libraries
  without JSpecify annotations count as unannotated, so their return values
  count as present. And the analysis is not complete in every case, for example
  for fields that a framework sets via reflection.
* **Error Prone as a linter.** NullAway runs as a plugin of Error Prone. The
  checks of Error Prone that are active by default stay switched on; that is the
  linting of the backend (xref:adr-011-qualitaetsgates-im-build[ADR-011]).

=== Context

ADR-018 requires that every type checks its required attributes. The code after
PR #59 additionally checked parameters in adapters and query methods, for
example `Validate.required(user, …)` in `HostPermissions` or in
`Snapshot.isExpired`. These checks repeat what the types already ensure, and
make the signatures less clear instead of clearer.

`Aktion` carried a flag stating whether it has a business reference. Every
caller had to check it at runtime and document the check in Javadoc and
`@throws`; the SPI carried the reference as `@Nullable`.

The packages were already `@NullMarked`, but nothing enforced it. The
annotation was documentation.

=== Decision Drivers

* Errors as early as possible, ideally at compile time.
* The signature says what is needed; code and Javadoc do not repeat it.
* Understandable messages where foreign values come in.
* Little additional effort in the build.

=== Considered Options

==== Option 1: Everyone checks their parameters

As before: types, adapters, use cases and queries check every parameter at
runtime. Understandable messages everywhere, but the same check in many
places, and an error only shows up at the call.

==== Option 2: Types check, NullAway secures the rest (chosen)

Only the types check, on creation. The compiler takes care of everything else:
NullAway for `null`, sealed types for distinguishing cases. One additional
compiler plugin in the build.

==== Option 3: Types check, otherwise only convention

Only the types check. `@NullMarked` stays documentation; nothing enforces it.
No additional tool, but an error inside only shows up as a
`NullPointerException` without an attribute name, somewhere after its cause.

=== Pugh Matrix

`+1` means better support, `0` neutral and `-1` weaker support. The matrix is
unweighted.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Errors detected early | 0 | +1 | -1
| Signature instead of repetition | -1 | +1 | +1
| Understandable message at the boundary | +1 | +1 | +1
| Little effort in the build | +1 | -1 | +1
s| Sum s| +1 s| +2 s| +2
|===

Options 2 and 3 have the same sum. The deciding factor is the owner’s
principle “fail fast through the compiler”: without a tool, dropping checks
inside would only be a promise.

=== Consequences

==== Positive

* Use cases and adapters contain only their logic. Whoever reads a signature
  sees what is needed.
* A host sees from the `AuthorizationRequest` whether a reference is included,
  and the compiler checks that it handles both kinds.
* `null` in a place that does not allow it is caught at compile time and not
  only in operation.
* Error Prone runs along with its default checks and, when it was introduced,
  already found a reference comparison in `VersionSequence`.

==== Negative

* Two more tools in the build (Error Prone, NullAway) that have to be checked
  as well on updates of JDK and Gradle.
* The SPI change breaks every host that compiled against the old `Aktion`.
  Before the first release, this affects only the tests of the library.
* With this decision, the role properties of the starter were named
  `standardschreiben.berechtigung.rollen.vorlagen.<AKTION>` and
  `….rollen.schreiben.<AKTION>`; the default authorities kept their names
  (`ROLE_SSW_*`). That is the state of this decision. Since ADR-024 (#84),
  properties and default authorities have different names; the section
  “Security” of the <<crosscutting-concepts>> gives the current state.

==== Neutral or Follow-Up

* New case distinctions in model and SPI are designed as a type first, not as a
  flag.
* The skill `skills/code-stil/SKILL.md` describes how an agent applies the
  rules when writing code; the solution strategy summarizes the code style.

=== Review Notes

The owner decided on 2026-11-22 in the review of PR #62:

* The promise “never a `NullPointerException`” applies at the boundaries.
* The checks of Error Prone that are active by default stay switched on in
  addition to NullAway; individual exceptions are justified specifically
  (xref:adr-011-qualitaetsgates-im-build[ADR-011]).
* The new names of the role properties fit.
* ADR-019 and its four relations are accepted.

The review also added `RequireExplicitNullMarking`, the JSpecify mode, the
probes in `checkNullContract` and the section “What NullAway does not
guarantee”.
