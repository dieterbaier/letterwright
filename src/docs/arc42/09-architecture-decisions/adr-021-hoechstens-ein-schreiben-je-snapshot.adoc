[[adr-021-hoechstens-ein-schreiben-je-snapshot]]
== ADR-021: At most one letter per snapshot

=== Status

Accepted on 2026-11-22.

The owner set the direction on 2026-11-22 in #53: the snapshot ID is the key.
The ADR was drafted with AI support. The owner accepted it and its three
relations on the same day in the review of PR #64, with the requirement that the
domain owns the rule and that the data context is released after saving.

=== Decision

* **The domain owns the rule.** A snapshot is *open* as long as no letter has
  been created from it, and *consumed* afterwards. `Letter.fromSnapshot`
  accepts only an open snapshot and returns the new letter together with the
  consumed snapshot. A consumed snapshot cannot be consumed again. This is
  tested in the domain model without a database.
* **The persistence secures the rule technically.** It stores the letter and
  the consumed snapshot in one step, and only if the stored snapshot is still
  open. Otherwise it stores nothing and reports the existing letter. A mere
  check beforehand is not enough, because concurrent requests both read an open
  snapshot.
* **A consumed snapshot no longer has a data context.** It keeps what a repeat
  needs: owner, business reference, template versions (for the authorization
  check) and expiry. The letter knows the snapshot ID. If saving fails for
  business reasons, the snapshot stays open with its data context.
* **Repeated saving is idempotent.** After a double click or a retry after a
  lost response, the user gets back the letter that is already stored
  (`AlreadySaved`), without the data context being read or a PDF being
  created. The time limit remains: after expiry, a repeat also requires a new
  preview.
* **Concurrent saving.** If the persistence reports that the snapshot is
  already consumed, it is certain that no letter refers to the request's own
  PDF. Only then does the request remove its PDF and return the other request's
  letter. If a new preview has meanwhile deleted the open snapshot, the
  persistence also stores nothing; the request removes its PDF and reports the
  snapshot as unknown.
* **Uncertain outcome.** If the persistence throws an exception, it is unknown
  whether the save happened. Then nothing is undone, not even the PDF. A repeat
  clarifies the outcome.
* **Order.** First snapshot, owner, expiry and permission, then the state of the
  snapshot. This way an unauthorized user does not learn whether a save already
  happened
  (xref:adr-020-zulaessige-kombination-aus-standardschreiben-und-bezug[ADR-020]).
* **An updated preview** deletes only an open snapshot of the same user. It
  leaves a consumed one in place, so that a repeat can still find it. Whether
  it is open is decided by the persistence itself when deleting, in the same
  step (conditional delete). A check beforehand is not enough: in between, a
  concurrent request can consume it.
* **Deleted letter.** If the letter of a consumed snapshot has meanwhile been
  hard deleted or logically deleted, a repeat finds nothing anymore and gets
  “snapshot unknown”. This also applies to a concurrent request that still read
  the snapshot as open: if the persistence reports a logically deleted existing
  letter or a hard deleted one (`LetterRemoved`), the request removes its PDF
  and reports the snapshot as unknown. A consumed snapshot without a visible
  letter is therefore not defective data. The letter is not created again; that
  requires a new preview. Added on 2026-11-22 with #54.
* **Deliberately creating anew** means: new preview, hence new snapshot, hence
  new letter.
* **Changed data context.** No PDF is created, and the snapshot stays open
  until a new preview replaces it or it expires.

=== Context

Saving is expensive: it renders a PDF, checks it against PDF/A-2b and PDF/UA-1
and stores it. A double click, a browser retry after a timeout or two open tabs
send the same request several times. Without a rule, several letters would be
created for the same preview, and the user would not know which one is valid.
After a lost response, the repeat must still return the ID of the letter, so
that the user interface can show the download link (#10). The rule must be
fixed before the persistence design (#6), because it requires a column and a
uniqueness rule in the database.

=== Decision Drivers

* A double click or retry does not create a second letter.
* A repeat after a lost response gets the result of the first attempt.
* A deliberate new creation remains possible.
* No additional concept that the frontend and the persistence have to carry.

=== Considered Options

==== Option 1: The snapshot ID is the key (chosen)

As above. The snapshot is unique anyway, bound to the user and time-limited; it
serves as a natural idempotency key. Its state change from open to consumed
makes the rule a rule of the domain model.

==== Option 2: The snapshot is consumed on saving

Saving deletes the snapshot; a second save does not find it. Simple, but a
repeat after a lost response only gets “unknown” instead of the ID of the
letter. Concurrent requests still need an atomic rule.

==== Option 3: Idempotency key of the client

The frontend sends a key per save attempt; the library remembers key and
result. Flexible, but another concept with its own storage and its own
lifetime, which every caller has to use correctly.

=== Consequences

==== Positive

* The user interface can repeat saving safely.
* The rule lives in the domain model and can be tested without a database; the
  persistence only enforces it against concurrent access.
* After saving, no data context remains in the snapshot.

==== Negative

* If a concurrent request wins, a PDF was created and checked for nothing. This
  is rare and only costs computing time.
* If the outcome is uncertain, or if removing a losing PDF fails, an orphaned
  document can remain in the document store. That is the price for never
  deleting the PDF of a stored letter.
* The state change and the letter must be stored in one transaction; snapshot
  and letter therefore live in the same persistence.

==== Neutral or Follow-Up

* #6: State of the snapshot with a conditional update from open to consumed, a
  column for the snapshot ID on the letter with a unique constraint, both in
  one transaction. The data context is removed when the snapshot is consumed.
  Deleting on update is conditional as well (only while open); a test against
  both databases proves that it does not delete a snapshot consumed
  concurrently.
* #10: For `AlreadySaved`, the user interface shows the same download link as
  for `Saved`.
* Whether orphaned documents must be cleaned up depends on the document store
  (#60).

=== Review Notes

On 2026-11-22, in the review of PR #64, the owner decided:

* ADR-021 and its three relations are accepted in their direction.
* The rule “at most one letter per snapshot” is owned by the domain as a state
  change. The persistence additionally enforces it atomically; a mere check
  beforehand or a unique constraint alone is not enough.
* After a successful save, no data context is kept just for the repeat. The
  metadata for the repeat remain.

The review also brought:

* If the outcome of saving is uncertain, the PDF is not removed. The first
  draft removed it on every exception.
* Deleting on update is conditional and atomic. The second draft checked the
  state beforehand and then deleted unconditionally; a concurrent save in
  between would have made the repeat impossible.

On 2026-11-22, in #54 (PR #66), the owner decided that a repeat after the
letter has been deleted gets “snapshot unknown”, and asked for the note in this
ADR. The decision above has been extended accordingly.
