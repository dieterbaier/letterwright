[[adr-013-styling-der-frontend-komponenten]]
== ADR-013: Styling of the frontend components: own styles, overridable by the host

=== Status

Proposed.

This ADR was created with AI assistance. It counts as an architecture decision
only once the responsible owner has reviewed and accepted it.

=== Decision

We propose:

* The React components bring **their own default styles**, generated with
  UnoCSS. The classes carry **their own prefix**, and there is **no global
  reset**. The package's CSS changes nothing outside its components.
* The styles sit in **their own CSS layer** (`@layer`). Host styles
  outside this layer therefore take precedence. The host can
  override without using `!important`.
* Public contract since the frontend scaffold (#13): the class prefix `lw-`,
  matching the table prefix `lw_`
  (xref:adr-006-datenbankagnostische-persistenz[ADR-006]), and the
  CSS layer `letterwright`. Changing them breaks hosts that address the classes
  or the layer in their CSS.
* Colours, fonts and spacing come from **CSS custom properties** with their own
  prefix. The host sets them; otherwise default values apply. This applies to the
  admin UI and to the controls of the display component, such as the
  notice and the button “Aktualisieren”.
* The **letter in the preview** is excluded. It follows only the central
  DOCX specification (QS-013) and is isolated from host styles and tokens, in an
  `iframe` (xref:adr-014-isolation-der-vorschau-im-iframe[ADR-014]).
* **Render props** for single building blocks, such as a button or an input field,
  are a later extension. They come only when a host wants to use its own
  components.

=== Context

The components run embedded in host applications
(xref:adr-001-einbettbare-bibliothek[ADR-001]) and are to adapt to their
look. The primary host application known so far is a React application with
UnoCSS. The owner wants own styles that the host can override, and considers
CSS custom properties suitable for the admin UI and the display component
(Q-ARCH-003, 2026-11-15).

=== Decision Drivers

* The components can be used at once without effort for the host, and they are accessible.
* The host can adapt the look to its design system.
* The package depends on no third-party component library.
* The package's CSS does not change the host application.

=== Considered Options

==== Option 1: Own styles in a CSS layer with design tokens

The library styles itself, reads tokens from CSS custom properties and gives the
host's styles precedence via `@layer`. Render props can be added later.

==== Option 2: Unstyled components (headless)

The library provides only behaviour and accessibility; the host styles everything
itself. Without effort by the host, the components look unfinished.

==== Option 3: The host's component library as a peer dependency

The library uses the UI components of a specific
component library. This fits hosts with this library exactly and binds
the package to its versions.

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker
support and `?` a rating that needs human review or
a prototype. If a column contains a `?`, its sum is `?` as well.

=== Consequences

==== Positive

* The components work at once and can be adapted step by step.
* The primary host application can override with its own UnoCSS.

==== Negative

* The names of the custom properties and the class prefix belong to the public
  contract of the package and must stay stable.
* If a host overrides colours, it can make contrasts worse. The library
  ensures accessibility only for the default appearance.

==== Neutral or Follow-Up

* The frontend scaffold (#13) sets up UnoCSS with a prefix, without a reset and with
  `@layer`.
* The custom properties are defined and documented with the first component of
  the user interface.
* The isolation of the preview is covered by
  xref:adr-014-isolation-der-vorschau-im-iframe[ADR-014].
