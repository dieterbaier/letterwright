== ADR-023: Saving a letter in a transaction of the host

=== Status

Accepted on 2026-11-23.

The owner set the direction on 2026-11-23: atomic callback only, callback only
on a new creation, business rejection as a sealed result. The ADR was drafted
with AI support. In the review of PR #74, the owner decided the open questions
on names and `REQUIRED`, asked for clarifications and deferred the file name.
After that, he accepted the ADR and its four relations on the same day.

=== Decision

The host can combine saving a letter atomically with its own database actions
in two ways. Both use the same use case `SaveLetter`, the same authorization
check (`ForCreation`) and the same idempotency according to
xref:adr-021-hoechstens-ein-schreiben-je-snapshot[ADR-021].

==== Java API, the primary way

* A separate module `api` with its own types and an inbound adapter, following
  the pattern from xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]. The
  host sees neither the domain model nor internal use case ports. The starter
  exports `api` next to `spi`.
* The host calls it in its own use case “save letter” with the user ID and
  the snapshot ID. It receives a sealed result with the same cases as
  `SaveResult`. Saved and already saved carry the identifiers that the callback
  also receives (see below).
* *Transaction (`REQUIRED`):* The library joins a running transaction. If none
  is running, it opens its own, and today's behaviour applies. Within a running
  transaction, it does not open an independent one (no `REQUIRES_NEW`). Saving
  is therefore atomic with further actions of the host only if the host opens
  the joint transaction before the call.
* The host evaluates the result, changes its own data and commits everything
  together. If it rolls back, the letter and the consumption of the snapshot
  roll back too. There is no callback on this way.

==== Saving through the user interface: optional synchronous callback

* `spi` gets the optional interface `spi.LetterSaveCallback`. If the host does
  not provide an implementation, the library behaves as it does today.
* *Transaction boundary:* When saving through REST, the endpoint of the library
  is the outer boundary of the transaction. The callback and the database
  actions of the host take part in it.
* *Timing:* The callback runs in the same transaction, after the database
  changes of the library and before the commit. There is no listener after the
  commit (`AFTER_COMMIT`).
* *Only on a new creation:* The callback runs only if the current call creates
  the letter. If it returns `AlreadySaved`, it creates no new letter and
  triggers no callback. The contract guarantees nothing more in this case: the
  existing letter may have been created through the Java API without a
  callback, or another call in the same outer transaction created it before the
  host commits.
* *Data:* The callback receives stable identifiers: the ID of the letter
  (technical key), through which the host links its data with the letter, the
  business reference, the letter template, the user ID and the time of
  creation.
* *Result:* The callback returns a `CallbackResult`, `Accepted` or `Rejected`
  with a reason for the user. In Spring, a return value alone does not trigger
  a rollback. On `Rejected`, the library therefore explicitly rolls back at its
  outer boundary and only after that reports a separate case of `SaveResult`
  with the reason. Inner, participating boundaries do not mark the transaction
  as rollback-only for this and then return normally. Otherwise an
  `UnexpectedRollbackException` displaces the business result, and the reason
  does not reach the user. The snapshot stays open as long as it does not
  expire, and the user can save again.
* *Exceptions:* Every exception of the callback is a technical error and also
  rolls back the joint transaction. The contract declares no checked
  exceptions.
* *No repeat by the library:* After an error, the transaction is only marked
  for rollback. The repeat is a new save attempt of the user.
* *Decoupled effects are the host's business:* If the host needs an effect
  outside its database, for example completing a task in a remote engine or
  filing in its own DMS, it writes an outbox job into the same transaction in
  the callback and then executes it itself, repeatably and idempotently.

==== File name

The file name is not part of this contract and is deferred (Q-ARCH-004,
question “file name”). For linking with the host's data, the ID of the letter
is enough. If a file name is added, it extends the result and the callback
without changing the guarantees of this ADR.

==== Responsibility boundary

As recorded in Q-ARCH-004: the library is responsible for its idempotency
according to ADR-021 and for the guarantees above. The host is responsible for
the idempotency of its own actions, for the interplay of its orchestration with
the callback, and for repeat, recovery and compensation of external side
effects. Idempotent saving by the library does not make the host's use case
idempotent.

=== Context

The host must be able to save a letter atomically together with its own
database actions, for example together with completing a human task
(Q-ARCH-004). Today it triggers saving only through the React components and
REST; ADR-016 assumes that it does not need a Java API.

Two integration needs exist side by side. A host that orchestrates itself wants
to call saving in its use case and evaluate the result as a return value. A
host whose user saves through the user interface of the library has no use
case of its own at that moment and needs a callback.

For the notification after saving, two semantics exclude each other. Atomic,
it runs before the joint commit, and an error rolls back everything.
Decoupled, it runs after the commit, the letter stays saved, and someone has to
repeat. A callback cannot deliver both.

Today, saving renders the PDF, checks it and stores it in the document store
before it stores the letter and the consumed snapshot in one step
(`SaveLetterService`, ADR-021). The document store does not take part in the
transaction.

=== Decision Drivers

* **Atomicity:** The letter, the consumption of the snapshot and the data of
  the host commit or roll back together.
* **Small contract:** few guarantees, few cases in the test, no workflow
  control in the library.
* **Robustness against errors of the host:** An error of the host leaves no
  contradictory state behind that the library would have to repair.
* **Integration effort of the host (QS-007):** no new mandatory interface,
  little configuration.

=== Considered Options

For the way through the Java API there is no alternative with a callback: the
host is already in its use case. The options concern saving through the user
interface.

==== Option 1: Atomic callback only (chosen)

As above. The host achieves decoupled effects with an outbox in the callback.

==== Option 2: Decoupled notification only

The library notifies the host after the commit (`AFTER_COMMIT` or its own
outbox). The letter stays saved even if the host's action fails. The library or
the host must repeat the notification, and the host must process it
idempotently. This does not meet the owner's tendency of 2026-11-22
(atomicity).

==== Option 3: Both, the host chooses per callback

The host chooses atomic or decoupled. The contract contains both semantics,
and every combination with the Java API, repeat and rejection must be tested.
What the host additionally achieves with this, it also achieves with option 1
and its own outbox.

=== Pugh Matrix

`+1` stands for better support, `0` for neutral, `-1` for weaker support. The
matrix is unweighted.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Atomicity | +1 | -1 | +1
| Small contract | +1 | 0 | -1
| Robustness against errors of the host | +1 | -1 | 0
| Integration effort of the host | 0 | 0 | -1
s| Total s| +3 s| -2 s| -1
|===

Option 2 gets `-1` for robustness, because a saved letter remains without the
corresponding action of the host until someone repeats. Option 3 gets `0`
there, because the host has the same problem in decoupled mode. For the
integration effort, option 1 stays neutral: the callback is optional; whoever
uses it implements one interface more. Option 3 additionally requires choosing
the semantics.

=== Consequences

==== Positive

* A host combines saving with its own actions atomically, whether it
  orchestrates itself or its users save through the user interface.
* The library stays free of workflow, repeat and compensation control. A
  process engine remains the host's business.
* A business rejection by the host reaches the user with a reason, instead of
  as a generic error.

==== Negative

* One more module for the Java API, with its own types and mapping, as
  described in ADR-016.
* The error path from ADR-021 becomes wider. If the host rolls back, the PDF is
  already in the document store, and no letter refers to it. This also applies
  if the Java API returns successfully and the host only rolls back afterwards;
  the library learns nothing about that.
* Rendering and conformance check run on saving today and thus lengthen the
  host's transaction.
* If the host does not share its transaction correctly with the library, for
  example with an embedded engine without a properly integrated transaction
  manager, atomicity is not given, without an error becoming visible.

==== Neutral or Follow-Up

* `SaveResult` gets a case for the rejection by the host, with a Gherkin
  scenario and a test.
* Cleanup of orphaned PDFs: belongs to the document store contract (#60) and
  to the persistence (#6).
* Separate preparing and committing, so that rendering and checking happen
  before a short write transaction (Q-ARCH-004). This is a deliberate
  restructuring of `SaveLetterService` and a decision of its own.
* Integration evidence in the host contract test:
** joint commit and later rollback by the host,
** saving through the Java API without an outer transaction,
** rejection and exception in the callback; for the rejection, the test checks
   the REST response with the reason and the state of both sides after the
   rollback,
** lost response with retry.
* ADR-016 and the building block view describe the Java API and the callback
  once this ADR is accepted. The host's obligations belong in the integration
  documentation (#11).

=== Assumptions

* The host and the library share one physical transaction through the same
  transaction manager. A shared data source alone is not enough.
* The library remains usable unchanged for hosts without a process engine and
  without a callback.

=== Open Questions

* None. The owner answered the three open questions of the first draft in the
  review of PR #74: module `api`, interface `spi.LetterSaveCallback` with
  `CallbackResult` (`Accepted`, `Rejected`); the Java API works with
  `REQUIRED`; the file name is deferred and is recorded in Q-ARCH-004.
