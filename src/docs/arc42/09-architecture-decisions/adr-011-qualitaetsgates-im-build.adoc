[[adr-011-qualitaetsgates-im-build]]
== ADR-011: Quality gates in the build

=== Status

Accepted on 2026-11-18.

This ADR was created with AI assistance. The owner accepted it when reviewing
Epic #4 (issue #37), together with its outgoing relations.

=== Decision

We use a **GitHub Actions pipeline** that fails on every pull request
if one of these gates is violated:

* **Coverage ≥ 80 % of lines *and* branches**, for **each** backend module (JaCoCo
  `jacocoTestCoverageVerification`) and **each** frontend package (Vitest
  `coverage.thresholds`). Generated code is excluded.
* **ArchUnit** rules for the hexagonal structure.
* **Linting**, in the frontend with ESLint, in the backend with Error Prone. Error Prone
  runs when the production code is compiled, with its checks that are active by
  default, plus NullAway for the null contract
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]). An
  exception turns off a single check at the smallest possible place with
  `@SuppressWarnings("<check>")` and justifies it in the comment next to it. The owner
  decides whether a check is turned off for the whole build.
* **veraPDF** for all reference PDFs (PDF/A-2b, PDF/UA-1). Planned: the step
  comes with the rendering pipeline (#7). Today it does not exist in `build.yml`.
* **axe-core** without violations of the levels *serious* and *critical*.
* **Architecture docs**: `./build.sh check-adapters` and `./build.sh build` (validates,
  generates and renders, including PlantUML) in the workflow
  `.github/workflows/architekturdoku.yml`. Only the state of `main` is published on
  **GitHub Pages**; pull requests only build.

Implementation (#14): the workflow `.github/workflows/build.yml` runs on every pull
request to `main` and on every push to `main`, with two jobs:

* *Backend:* `./gradlew build` with the validated wrapper on Java 21 (baseline)
  and Java 25. The build includes tests, the JaCoCo gate per module, ArchUnit and
  Error Prone with NullAway.
  Test and coverage reports are kept as an artifact.
* *Frontend:* `npm ci`, `npm run lint`, `npm run build` and `npm test` on
  Node 22.22.2 (lower bound from `engines.node`) and on the newest versions of the
  lines 24 and 26. `npm test` contains the Vitest gate and the axe check. The
  coverage report is kept as an artifact.

The workflow always builds both. A filter by changed paths does not pay off at
about one minute of run time per job. veraPDF is added with the rendering pipeline
(#7).

=== Context

Issue #1 asks for 80 % test coverage. The owner makes this precise: it applies to both (lines and
branches) and everything (backend and frontend) and is to be checked.

=== Decision Drivers

* Coverage measurable and not negotiable.
* Early feedback in the PR.
* Securing conformance permanently.

=== Considered Options

==== Option 1: Gates per module in GitHub Actions

Local outliers show up at once. Stricter, occasionally annoying for small modules.

==== Option 2: Gates aggregated across the repository

More tolerant; weakly tested modules can hide behind well tested ones.

==== Option 3: Reports only, no gates

Nothing is blocked, but the requirement from the issue is not ensured.

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker
support and `?` a rating that needs human review or
a prototype. If a column contains a `?`, its sum is `?` as well.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Requirement reliably met | +1 | 0 | -1
| Early feedback | +1 | +1 | 0
| Low friction | -1 | 0 | +1
s| Sum s| +1 s| +1 s| 0
|===

=== Consequences

==== Positive

* Quality goals are visible and enforced in every PR.

==== Negative

* Longer CI run time because of Testcontainers and veraPDF.

==== Neutral or Follow-Up

* Set up the pipeline in the first build epic, before domain code is written.

The owner set linting in the backend with Error Prone as a gate on 2026-11-22 in

(issue #37), with the scope of the decision above. This includes the
exclusion of generated code from the coverage gate. Today there is no
generated code and therefore no exclusion rule in JaCoCo or Vitest. Such a
rule is configured only once generated code appears, and is
then visible in the build script.
