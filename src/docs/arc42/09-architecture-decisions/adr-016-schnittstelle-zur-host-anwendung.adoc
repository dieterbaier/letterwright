[[adr-016-schnittstelle-zur-host-anwendung]]
== ADR-016: Cut and data types of the interface to the host application

=== Status

Accepted on 2026-11-17.

This ADR was created with AI assistance. The owner reviewed and accepted it in
the review of PR #28.

=== Decision

The interface to the host application is a separate module `spi` with its own
data types (option 3):

* **`spi`** (directory `src/application/backend/spi`) contains the interfaces
  that the host implements: `PlaceholderDataProvider`, `AuthorizationCheck`
  and `DeletionPolicy` (ADR-002). In addition there are separate data types for
  everything that flows through these interfaces, for example the business
  reference, the data context and the request to the authorization check. The
  module is plain Java without Spring and depends on no other module of the
  library.
* **`usecases-out`** now contains only internal ports: repositories,
  `DocumentStore`, `Renderer`, `ConformanceChecker` and the ports through which
  the core requests placeholder data, permission and deletion policy in domain
  terms. No host implements `usecases-out`.
* **`adapter-host`** (directory `adapter/out/adapter-host`) is an outbound
  adapter. It implements these internal ports, calls the host's SPI
  implementations and maps between SPI types and the domain model. Apart from
  the starter it is the only module that knows `spi`.
* **`spring-boot-starter`** exports only `spi` via `api`. It includes all other
  modules as `implementation`. A host that includes the starter sees only `spi`
  of the library at compile time; it gets ports, use cases, domain model,
  domain services and adapters only at runtime.
  Addendum 2026-11-23: With xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] the starter
  additionally exports the module `api` of the Java API.
* The default implementation of `AuthorizationCheck` on Spring Security
  implements the SPI interface like any host implementation. It lies in the
  starter and steps back as soon as the host provides its own bean.
* There is no inbound Java API for the host. The host uses the library through
  the React components and the REST endpoints of `adapter-web` and provides
  data to it through `spi`.
  Addendum 2026-11-23: superseded by xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]. For saving in
  its own transaction the host gets a Java API following the pattern of
  this ADR: a separate module `api` with its own types and an inbound
  adapter. For this, `spi` gets the optional interface
  `spi.LetterSaveCallback`.

The cut:

[cols="1,2,2", options="header"]
|===
| Module | Directory | Depends on
| `spi` | `spi` | nothing
| `usecases-out` | `usecases/out` | `domain-model` (`api`)
| `adapter-host` | `adapter/out/adapter-host` | `usecases-out` and `spi` (`implementation`)
| `spring-boot-starter` | `spring-boot-starter` | `spi` (`api`), all other modules (`implementation`)
|===

Addendum 2026-11-23: The table shows the original cut. With
xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] the planned
modules `api` and `adapter-api` are added. Like `spi`, `api` depends on
nothing. The starter then exports `spi` and `api` via `api` and keeps
`adapter-api`, like all other modules, internal via `implementation`.

Addendum 2026-11-24: Both modules were created with #78 and are no longer
planned. The starter exports `spi` and `api` via `api`; it includes
`adapter-api` via `implementation`. `adapter-api` depends on `api`,
`usecases-in` and Spring Transaction (`implementation`).

ArchUnit checks in addition, each rule with a fixture:

* `spi` depends on no other package of the library.
* Domain, ports and use cases do not know `spi`.
* Only `adapter-host` and the starter use `spi`.

Addendum 2026-11-24: For the Java API from
xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] the
corresponding rules apply, also with a fixture: `api` depends on no other
package of the library, not even on `spi`, and only `adapter-api` and the
starter use `api`. `host-contract-test` checks that a host sees `spi` and `api`
at compile time and nothing else.

=== Context

ADR-002 calls `usecases-out` the SPI. Today it holds two kinds of ports side by
side: the three ports that the host implements, and the ports that the
library's outbound adapters implement. `usecases-out` exports the domain model
via `api` (`src/application/backend/usecases/out/build.gradle.kts`). A host
that implements a port therefore works with the types of the domain model and
at the same time sees all internal ports.

The starter exports `usecases-in` and `usecases-out` via `api`
(`src/application/backend/spring-boot-starter/build.gradle.kts`). A host that
includes the starter thus sees all use cases, all ports and the domain model at
compile time. The narrow host dependency from
xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015] applies only to
a host module that depends directly on `usecases-out`, and even there it
includes the domain model.

This makes the domain model part of the public API. Every renaming or
restructuring in the model breaks host implementations, and the model can no
longer evolve freely. ADR-002 already calls the SPIs public API that needs
versioning.

On 2026-11-17 the owner proposed a separate SPI module, shielded from the use
case interfaces, without a dependency on the domain model, with its own data
types and a mapping from and to the domain model. In his assessment the host
does not need an inbound Java API.

There is no domain code in the ports yet (epic #5 is pending). The cut can
therefore be changed now without reworking existing implementations.

=== Decision Drivers

* **Stable host API:** Changes to the domain model break no host
  implementation.
* **Narrow dependency of the host:** At compile time the host sees only what
  it must implement or pass.
* **Internal ports freely changeable:** Ports that only adapters of the library
  implement are not a contract with the host.
* **Low effort:** Few modules, few duplicated types and little mapping code.
* **Integration effort of the host:** The number of interfaces to implement and
  the configuration stay within QS-007.

=== Considered Options

==== Option 1: Host ports stay in `usecases-out`

The current cut. No additional module, no mapping. The host works with the
domain model and sees all internal ports. Via the starter it additionally sees
all use cases. Every change to the model or the internal ports is potentially
incompatible for the host.

==== Option 2: Separate module `spi` with the types of the domain model

The three host ports move into a separate module that depends on the domain
model via `api`. The core calls them directly; no mapping is needed. The
internal ports and the use cases are invisible to the host, but the domain
model remains part of the public API. In addition, the core depends on a
module whose changes the host must go along with.

==== Option 3: Separate module `spi` with its own data types (chosen)

Like option 2, but `spi` depends on nothing. The data types of the interface
are separate, immutable types (records). An outbound adapter `adapter-host`
maps, just as every other outbound adapter translates between its technology
and the ports. The core does not know `spi`.

Costs: one more module for `spi` and one for `adapter-host`, duplicated types
for the data that flows through the interface, and mapping code with tests.
Hombergs names exactly these costs: the finer the cut, the more mapping
between the modules (see xref:adr-015-literatur[literature in ADR-015]).

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker support and `?` a rating
that needs human review or a prototype. If a column contains a `?`, its sum is
also `?`. The matrix is unweighted.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Stable host API | -1 | -1 | +1
| Narrow dependency of the host | -1 | 0 | +1
| Internal ports freely changeable | -1 | +1 | +1
| Low effort | +1 | 0 | -1
| Integration effort of the host | 0 | 0 | 0
s| Sum s| -2 s| 0 s| +2
|===

Option 2 gets `0` for the narrow dependency, because the host no longer sees
the ports and use cases, but still sees the domain model. The options do not
differ in integration effort: in all three the host implements the same three
interfaces.

=== Consequences

==== Positive

* The domain model is no longer public API and can change without breaking
  host implementations.
* At compile time a host sees only `spi` of the library, even if it includes
  the starter. If it calls a use case or a repository by mistake, its code does
  not compile.
* The public API can be read off one module. What is not in `spi` is not
  part of the contract with the host.
* Addendum 2026-11-24: Since
  xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] and #78 the
  host sees `spi` and `api` at compile time. Neither depends on any other
  module of the library; what is in neither of them is not part of the contract
  with the host. The two points above apply accordingly.
* The core knows no host types. The mapping lies in one place, in an adapter
  that, like any other, is replaceable and testable.

==== Negative

* Duplicated types and mapping code between `spi` and the domain model, with
  their own tests. Every new piece of data that the host delivers changes both
  sides and the mapping.
* Two more modules in the build.
* Errors in the mapping do not show up at compile time, but only in the
  tests of `adapter-host`.

==== Neutral or Follow-Up

* Issue #27 implemented the cut, before #19. The rule on the isolation of the
  adapters from #19 covers `adapter-host`.
* ADR-002 and ADR-009 describe where the host ports lie. Both were aligned and
  accepted with PR #28; the building block view was aligned as well.
* This ADR refines the statements of ADR-015 on the narrow host dependency
  (“ports and, transitively, the domain model”). With #19 the references in
  ADR-015 have been switched to `spi` as the host dependency.
* The example application (epic #11) demonstrates the contract with an
  implementation against `spi`.

=== Assumptions

* The host does not need an inbound Java API. It operates the library through
  the React components and REST (assessment of the owner on 2026-11-17).
  Addendum 2026-11-23: The assumption no longer holds, see
  xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023].
* The host passes the domain key and the file name from Q-ARCH-004 through
  the frontend components and thus through REST, not through Java. If it does
  need a Java call for this after all, an inbound API following the same
  pattern is added: a separate module with its own types and an inbound adapter.
  Addendum 2026-11-23: The owner has deferred the file name
  (Q-ARCH-004). The Java API is added for saving in a transaction of the
  host (xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]).
* The types that flow through the interface are few and flat
  (reference as type and ID, data context as values, yes/no decisions). This
  keeps the mapping small.

=== Open Questions

* None. The owner answered both questions in the review of PR #28:
** *Versioning of `spi`:* We start with one version for the whole
   package. Separate versioning of `spi` is not needed for now.
** *Location of the default `AuthorizationCheck`:* The starter is enough for
   now; a separate module is not needed.
