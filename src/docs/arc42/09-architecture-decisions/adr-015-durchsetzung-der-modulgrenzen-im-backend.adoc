[[adr-015-durchsetzung-der-modulgrenzen-im-backend]]
== ADR-015: Enforcing the architecture boundaries in the backend

=== Status

Accepted on 2026-11-16.

This ADR was created with AI assistance. The owner reviewed and accepted it in
the review of PR #18.

Extended on 2026-11-16 with the separation of domain model and domain services
(<<adr-015-domaenenservices>>, issue #25). The owner decided this extension:
option 1 of three variants, both modules under `domain`.

Refined on 2026-11-17 by xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016] (PR #28).
Since then `usecases-out` is an internal module; the host compiles only against
the module `spi`, also via the starter. With issue #19 the statements of this
ADR on the host dependency have been switched to `spi`.

Extended on 2026-11-18 with issue #19 (<<adr-015-leere-selektoren>>): an
ArchUnit rule checks the isolation of the adapters, and empty selectors fail.
So that ArchUnit also sees packages without further classes,
`-Xpkginfo:always` compiles every `package-info`. Independently of this, every
package is annotated with JSpecify `@NullMarked` (<<adr-015-null-vertrag>>).
The owner decided both in the review of PR #33. The extension was worded with
AI assistance; the owner accepted it in the review of PR #33.

=== Decision

We enforce the boundaries of the hexagonal architecture
(xref:adr-002-hexagonale-architektur-und-ports[ADR-002]) through **separate
Gradle modules** and not only through a package convention:

* Every boundary across which a dependency may run in one direction only is a
  module boundary: `domain-model`, `domain-service`, `usecases-in`,
  `usecases-out`, `usecases-service`, `spi` and one module per adapter (cut in
  xref:adr-009-build-monorepo-und-versionen[ADR-009] and
  xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]).
* Domain model and domain services are separate modules under `domain`. Only
  `usecases-service` includes `domain-service`, as `implementation`. Ports and
  adapters see only the model at compile time
  (<<adr-015-domaenenservices>>).
* The allowed directions are project dependencies in the
  `build.gradle.kts` files. An inbound adapter sees only `usecases-in`, an
  outbound adapter only `usecases-out`. A wrong dependency therefore fails at
  compile time (“fail fast”) and not only in the test run.
* **ArchUnit remains in addition** (module `architecture-tests`). At package
  level it checks part of the same rules and also what the module dependencies
  do not express: the domain and the ports are free of Spring, inbound and
  outbound ports do not know each other, the service knows no adapters,
  inbound adapters know only inbound ports, outbound adapters only outbound
  ones, no adapter depends on the starter, and no adapter uses another one.
  The domain model knows no domain services, and neither ports nor adapters
  know them. The rules on `spi` are in
  xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]. No rule allows an
  empty selector (<<adr-015-leere-selektoren>>).
* Shared build rules are in the convention plugin
  `letterwright.java-module`, so that the number of modules does not multiply
  the maintenance effort.

The unweighted Pugh matrix gives no clear winner (see below). The deciding
factor is the two drivers that the owner weights higher: early error detection
and the narrow dependency of the host.

=== Context

The backend skeleton (issue #12, PR #15) cut the use cases into three modules
`usecases/in`, `usecases/out` and `usecases/service`. ADR-002 and ADR-009
record this result, but do not justify why modules instead of a package
convention in one module. This ADR provides that justification.

Evidence checked in the repository:

* `src/application/backend/**/build.gradle.kts`: `adapter-web` depends only on
  `usecases-in`, `adapter-rendering` and `adapter-persistence-jdbc` only on
  `usecases-out`, `adapter-host` on `usecases-out` and `spi`;
  `usecases-service` exports `usecases-in` via `api` and
  uses `usecases-out` and `domain-service` via `implementation`;
  `spring-boot-starter` exports only `spi` via `api` and includes ports, service
  and adapters as `implementation` (addendum 2026-11-24: since #78 also
  `api`; `adapter-api` depends on `api` and `usecases-in`). It does not see
  `domain-service` at compile time; it only brings it along transitively at
  runtime.
* `src/application/backend/architecture-tests/`: the ArchUnit rules, each with
  a fixture that reproduces a violation.

Two properties of the project make the question sharper than in an ordinary
application:

* **It is a library** (xref:adr-001-einbettbare-bibliothek[ADR-001]).
  The driven ports are public API that the host implements. What lies in which
  artifact is therefore part of the contract with the host.
* **Ports and their implementations must be `public`.** Driving adapters
  call ports from other packages, and the auto-configuration in the starter
  must instantiate the service classes. Within one module the compiler
  therefore cannot prevent an adapter from directly using a service class or
  a foreign port.

=== Decision Drivers

* **Early error detection:** A wrong dependency should fail as early as
  possible, ideally already in the IDE and at compile time.
* **Narrow dependency of the host:** To compile, a host should need only the
  contract it implements, not the use cases, the service and the adapters. At
  runtime the host includes everything via the starter anyway. At the time of
  the first decision these were the ports and the domain; since
  xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016] it is only `spi`.
  Addendum 2026-11-24: since
  xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] (#78) `spi`
  and `api`.
* **Isolated adapters:** An adapter should not be able to use another one
  directly, for example the web adapter should not use persistence while
  bypassing the use cases. This driver was added only when reading the
  literature.
* **Low build effort:** Few modules, simple configuration.
* **Moving boundaries later:** How easily the cut can be changed if boundaries
  turn out to be wrong.
* **Compatibility with Spring hosts:** No extra hurdles for hosts that run on
  the classpath.

=== Considered Options

==== Option 1: One module, package convention and ArchUnit

All core classes lie in one module; the boundaries are packages. ArchUnit
checks the dependency rules after compilation in the test run.

Simplest build; boundaries can be moved with a refactoring. But a violation
shows up only in the test, and the IDE keeps offering the wrong class through
auto-completion. The host gets a single artifact with all classes. Both sources
consider checks after compilation alone too weak: Hombergs calls them “not
fail-safe”, because a single renamed package can make a rule run empty. Brown
calls them “fallible” with a feedback loop that is too long (see
<<adr-015-literatur>>).

==== Option 2: One module, visibility (package-private) and ArchUnit

Like option 1, but everything that does not have to cross a boundary is
package-private. The compiler thus enforces part of the rules.

This is Brown's preferred way for a monolith (“package by component”): the
fewer types are `public`, the more rules the compiler enforces. Within a
component this helps. At the boundaries of the hexagon it does not hold:
ports and service classes must be `public` (see Context), and that is exactly
where the important rules run. Hombergs names two further limits.
Package-private does not reach across subpackages. With Spring it only works
if the classes are created by classpath scanning. The host still gets a single
artifact.

==== Option 3: Separate Gradle modules per boundary and ArchUnit (chosen)

The boundaries are modules, the allowed directions are project dependencies.
ArchUnit checks in addition.

Wrong dependencies fail at compile time, and the IDE does not even offer them.
At compile time a host depends only on the module that contains its contract;
since xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016] that is
`spi`. The cut corresponds to the
finest variant that Hombergs describes: inbound and outbound ports as separate
modules, so that every adapter can be recognized as inbound or outbound by its
dependency alone. One module per adapter also avoids Brown's “Périphérique
anti-pattern”. This means infrastructure code in a shared source tree, through
which a web controller can call a repository directly, bypassing the domain.

Costs: more build files, a convention plugin, and moving a boundary is a change
to the build and to the published artifacts. Brown calls a separate source tree
per component “very much an idealistic solution” with costs for performance,
complexity and maintenance.

==== Option 4: Java modules (JPMS) with `module-info.java`

Every Gradle module additionally gets a module descriptor that exports only the
port packages.

Strongest encapsulation, even within one artifact: Brown describes this as a
distinction between types that are `public` and types that are “published”.
But it requires the same
split into artifacts as option 3 and takes effect only on the module path.
Spring Boot hosts usually run on the classpath, where the descriptors are
ignored. The effort for reflection access (`opens`) in tests and
auto-configuration has not been tried out.

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker support and `?` a rating
that needs human review or a prototype. If a column contains a `?`, its sum is
also `?`. The matrix is unweighted.

[.pugh-matrix]
[cols="2,1,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3 | Option 4
| Early error detection | -1 | 0 | +1 | +1
| Narrow dependency of the host | -1 | -1 | +1 | +1
| Isolated adapters | -1 | 0 | +1 | +1
| Low build effort | +1 | +1 | -1 | -1
| Moving boundaries later | +1 | +1 | -1 | -1
| Compatibility with Spring hosts | 0 | 0 | 0 | 0
s| Sum s| -1 s| +1 s| +1 s| +1
|===

The `0` for option 4 under “Compatibility with Spring hosts” is an estimate by
the owner without own experience with JPMS, not a tested rating (see
Assumptions).

Unweighted, option 2, option 3 and option 4 are level. Without the driver
“Isolated adapters”, which was added later, option 2 would be ahead.
But option 2 misses exactly the two drivers that the owner weights higher:
it enforces nothing at the boundaries of the hexagon, and the host gets all
classes. Option 3 and option 4 meet both. The matrix does not separate them,
because option 4 requires option 3 and, on a three-point scale, also gets `-1`
for build effort. Option 4 additionally costs the module descriptors and the
access grants for Spring. Its added value, encapsulation within one artifact,
takes effect only on the module path and therefore not in the expected hosts.
This is why option 3 is chosen.

[[adr-015-domaenenservices]]
=== Extension: domain model and domain services

On 2026-11-16 the owner pointed out a gap in the cut. Both port modules pass
on the domain via `api`. If a domain service lay in the same module as the
model, the ports and, transitively, all adapters would see it. An adapter could
then call it while bypassing the use case. The module boundaries did not
prevent this, and ArchUnit did not check it.

Three variants were considered:

. *Separate module for domain services* (chosen). Only `usecases-service`
  includes it. Ports and adapters do not see it at compile time.
. *Domain services in the module `usecases-service`.* They would be just as
  invisible, but domain logic would lie in the application layer.
. *Leave domain services in the domain and secure them only via ArchUnit.* This
  is the simplest, but fails only in the test and thus contradicts this ADR's
  early error detection.

The cut:

[cols="1,2,2", options="header"]
|===
| Module | Directory | Depends on
| `domain-model` | `domain/model` | nothing
| `domain-service` | `domain/service` | `domain-model` (`api`)
| `usecases-in`, `usecases-out` | `usecases/in`, `usecases/out` | `domain-model` (`api`)
| `usecases-service` | `usecases/service` | `usecases-in` (`api`), `usecases-out` and `domain-service` (`implementation`)
|===

Whether a domain service is visible is thus defined by the build and not by a
convention. Two ArchUnit rules additionally check this at package level, each
with a fixture: the model (`domain.model`) knows no domain services
(`domain.service`), and ports and adapters do not know them. The starter
includes `usecases-service` as `implementation`. It therefore does not see the
domain services at compile time, and a host using the starter also gets them
only at runtime. If the auto-configuration later needs them as beans, the
starter must include `domain-service` explicitly.

[[adr-015-leere-selektoren]]
=== Extension: isolation of the adapters and empty selectors

The review of PR #18 found two gaps in the ArchUnit check (issue #19). Both are
closed with this extension.

*Isolation of the adapters.* The rule `adaptersAreIsolatedFromEachOther` cuts
`adapter.<direction>.<adapter>` into slices, and no slice may depend on another.
It covers inbound and outbound adapters, including `adapter-host`.
Two fixtures reproduce the violation: an inbound adapter that uses an outbound
one, and `adapter-host` using another outbound adapter.

*Empty selectors.* No rule sets `allowEmptyShould(true)` any more. If a selector
matches no class in the production check, the check fails.

*Visibility of the packages.* The modules of the skeleton contain only
`package-info.java`. Without an annotation the compiler normally generates no
class from it. For ArchUnit the modules were empty, and all production checks
would have been red. The convention plugin therefore passes `-Xpkginfo:always`.
This turns every `package-info.java` into a class, with or without an
annotation.

Four variants were considered:

. *`-Xpkginfo:always`* (chosen). Visibility for ArchUnit depends on a compiler
  option and not on an annotation. The null contract is decided separately
  (<<adr-015-null-vertrag>>).
. *Only JSpecify `@NullMarked`.* The annotation also generates
  `package-info.class`. But visibility for ArchUnit would then depend on the
  null convention: a package without `@NullMarked` would drop out of the check.
. *Split #19* and introduce the ban on empty selectors only once real classes
  are in the modules (after #30). Until then the gap would stay open, precisely
  while #5 creates the first classes.
. *Allow empty selectors per rule* as long as their package is empty, with a
  list in the test. This costs maintenance, and the list can become outdated.

*What the evidence covers.* With a deliberately wrong base package, all checks
in `HexagonalArchitectureTest` fail with “failed to check any classes”, with
`-Xpkginfo:always` alone as well as with `@NullMarked` alone. This proves: a
selector that matches *nothing at all* any more is noticed. It does not prove
that every single package is matched. Many rules select several packages at
once, for example `domain..`, `adapter..` or the slice pattern
`adapter.(*).(*)..`. If a single package drops out of such a selector because
it was renamed, and others still match, the rule stays green. The weakness
that Hombergs names is thus reduced, but not removed.

[[adr-015-null-vertrag]]
=== Extension: null contract with JSpecify

Every package is annotated with JSpecify `@NullMarked` in its
`package-info.java`. Types are thus non-`null` by default; exceptions carry
`@Nullable`. The owner decided this in the review of PR #33 as a deliberate
contract, above all for `spi`: there the host sees what it must deliver and
what it receives. With a suitable toolchain, for example a nullness checker,
it can check its implementation against it. Spring Boot 4 uses JSpecify
itself.

What this means and what it does not:

* `javac` does not check the contract. The annotations are information for
  tools and readers.
* Subpackages do not inherit `@NullMarked`. Every new package needs its own
  `package-info.java` with `@NullMarked`. This is a convention for new
  packages. Neither ArchUnit nor the build checks it; ArchUnit only checks that
  the selectors match classes (<<adr-015-leere-selektoren>>).
* The convention plugin includes `org.jspecify:jspecify` via `api`, as
  JSpecify recommends for libraries. The version is in the
  version catalog, independent of the Spring Boot BOM. JSpecify does not need
  Spring.

=== Consequences

==== Positive

* A domain service is visible at compile time only in `usecases-service`.
  A port or adapter that imports it does not compile.

* Wrong dependencies fail at compile time and are not even offered in the
  IDE.
* At compile time a host sees only `spi`, even if it includes the starter
  (xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]; addendum 2026-11-24:
  since xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023] `spi` and
  `api`). The starter brings domain model,
  ports, use cases, service and adapters along only at
  runtime.
* For the rules that both cover, ArchUnit and module boundaries check in two
  ways; if one fails, the other remains. Hombergs recommends this
  combination.
* Every new module dependency is in the build script and is thus a deliberate
  decision that is visible in the review.
* The ArchUnit fixtures in the package `archfixture` prove that every rule
  detects the reproduced violation. A selector that matches nothing at all any
  more in the production code makes the production check fail
  (<<adr-015-leere-selektoren>>).
* The null contract applies from the start and is visible to the host in `spi`
  (<<adr-015-null-vertrag>>).

==== Negative

* More Gradle projects and build files; the convention plugin is mandatory,
  so that the rules do not drift apart.
* Moving a boundary changes the build and the published artifacts
  (xref:adr-012-distribution-ueber-github-packages[ADR-012]) and is therefore
  visible to hosts. Hombergs warns that build modules are “less supple to
  change over time” and that a wrong cut is therefore more likely to remain.
* The module dependencies themselves are code that can be wrong. An additional
  project dependency silently lifts a boundary. ArchUnit catches this only for
  the rules it checks. Since #19 the isolation of the adapters is one of
  them.
* A selector over several packages stays green if only one of them drops out
  and others still match (<<adr-015-leere-selektoren>>).
* Every module depends on JSpecify, and a host sees it via `spi`. The
  library contains only annotations and has no further dependencies.
* No tool checks whether a new package carries `@NullMarked`. This remains a
  convention that must be noticed in the review (<<adr-015-null-vertrag>>).

==== Neutral or Follow-Up

* Issue #32: The evidence at the host shows that `spi` brings JSpecify onto the
  compile classpath without passing on constraints from the Spring Boot BOM.
* Re-evaluate JPMS (option 4) if a host runs on the module path or
  encapsulation within one artifact becomes necessary.
* Within a module, package-private remains the default for everything that
  does not have to cross a boundary.

[[adr-015-literatur]]
=== Literature

Both sources have been checked against the original text. Quotations are given
in the English original.

*Tom Hombergs: _Get Your Hands Dirty on Clean Architecture_, 2nd edition. Packt,
2023, ISBN 978-1-80512-837-3, chapter 12 “Enforcing Architecture Boundaries”.*
The chapter presents three means side by side, each with its own section:
“Visibility modifiers”, “Post-compile fitness function” and “Build artifacts”.

* On build modules: “Developers can no longer inadvertently create illegal
  dependencies because the classes are not even available on the classpath and
  they would run into compile errors.” As further advantages he names that
  build tools do not allow cyclic dependencies, that modules can be changed in
  isolation, and that a new dependency becomes “a conscious act instead of an
  accident”.
* On the costs: the architecture “should be somewhat stable before splitting it
  into different build modules”, and build modules “tend to be less supple to
  change over time”. The finer the cut, the more mapping between the
  modules.
* On ArchUnit: checks after compilation “are not fail-safe”; a typo or a
  renamed package can make a rule ineffective.
* Conclusion of the chapter: “All three approaches can be combined to enforce
  architecture boundaries”.

*Simon Brown: “The Missing Chapter”. Chapter 34 in Robert C. Martin: _Clean
Architecture. A Craftsman's Guide to Software Structure and Design_. Prentice
Hall, © 2018 Pearson Education, ISBN 978-0-13-449416-6, pp. 303–321.*

* On checks after compilation (p. 313): “The problem with both approaches
  is that they are fallible, and the feedback loop is longer than it should be.”
  and “I'd personally like to use the compiler to enforce my architecture if at
  all possible.”
* On visibility (p. 318): with “package by component” only the component
  interface is `public`, “so we can rely on the compiler to enforce this
  architectural principle.” For ports and adapters he states that the port
  interfaces must be `public`.
* On separate source trees (pp. 319–320): dependencies can be decoupled “at the
  source code level”, “by configuring separate modules or projects in
  your build tool (e.g., Maven, Gradle, MSBuild)”, ideally with a separate
  source tree per component. He calls this “very much an idealistic
  solution” because of “real-world performance, complexity, and maintenance
  issues”.
* On only two source trees, domain and infrastructure (pp. 320–321): the
  “Périphérique anti-pattern of ports and adapters”. There, infrastructure code
  can call other infrastructure code while bypassing the domain.
* On module systems (p. 319): with OSGi or the Java 9 module system one can
  distinguish between “public” and “published”.

Both authors therefore prefer the compiler to checks after compilation. They
differ in the means. In a monolith, Brown relies first on visibility within one
source tree and considers separate modules per component expensive. Hombergs
recommends build modules as soon as the architecture is stable enough.

=== Assumptions

* The hosts run on the classpath (Spring Boot in standard operation).
* The module cut from ADR-009 is stable enough for the MVP that the costs of
  moving it rarely arise.
* JPMS (option 4) does not hinder Spring hosts on the classpath. This is the
  owner's estimate without own experience, not tested.

=== Open Questions

* None. Whether `usecases-out` is versioned separately from the starter was
  answered by the owner in the review of PR #18: not for now. All modules are
  released with the same version.
