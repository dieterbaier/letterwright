[[adr-002-hexagonale-architektur-und-ports]]
== ADR-002: Hexagonal architecture with ports to the host application

=== Status

Accepted on 2026-11-17.

This ADR was created with AI assistance. The owner reviewed and accepted it in
the review of PR #28.

=== Decision

We use a **hexagonal architecture** (Ports and Adapters) following DDD:

* **Domain** (without Spring): letterhead, letter template, template version,
  letter, placeholders, building blocks.
* **Application**: use cases such as “create preview”, “save letter”,
  “download letter”, “publish template”. Their interfaces are the
  **driving ports** (module `usecases-in`); their implementation lives
  separately (module `usecases-service`).
* **SPI to the host application** in its own module `spi`, with its own data
  types and without a dependency on the domain model. The host implements:
** `PlaceholderDataProvider`: delivers the data context for a letter template
   and a business reference (e.g. customer 4711). Values may already be
   formatted.
** `AuthorizationCheck` (default implementation on Spring Security in the
   starter): decides on maintaining, creating, viewing, downloading and
   deleting.
** `DeletionPolicy`: decides whether and how a letter is deleted
   (hard, logically, blocked), see retention periods.
* **Driven ports** in the module `usecases-out`, implemented only by adapters
  of the library:
** Ports for placeholder data, permission and deletion policy in domain terms
   (adapter `adapter-host`, maps to the SPI).
** `DocumentStore` (adapter, default JDBC/BLOB, later object storage).
** `TemplateRepository`, `LetterRepository` (adapter JDBC).
** `Renderer` and `ConformanceChecker` (adapters, see ADR-004 and ADR-005).
* **Driving adapters**: REST controllers and Spring Boot auto-configuration.

xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016] gives the reasons for
the cut and the data types of the SPI.

**Framework-free domain** (made more precise on 2026-11-21 in the review of
PR #57, accepted by the owner):
The domain stays independent of application, DI and persistence frameworks. Its
business behaviour must be executable and testable without containers, proxies
and technology integration. External libraries are assessed one by one by
purpose, transitive dependencies, influence on the model and effort to replace
them. Purely descriptive annotations or general helper libraries can be
explicitly allowed; this does not mean a blanket approval of further
dependencies. Code generation is assessed separately, even if it creates no
runtime dependency. Spring components stay outside the domain; Spring can
instantiate pure domain services from the outside through the configuration.

Currently allowed:

* JSpecify for the null contract (xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015]).
* The DDD annotations from `jmolecules-ddd`
  (xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018]).
* The project's own module `validation` (ADR-018).

This does not approve any other library, Lombok included. A rule in the
ArchUnit tests checks this list.

The module boundaries enforce the direction of dependencies at compile time:
driving adapters know only `usecases-in`, driven adapters only `usecases-out`
(ADR-009). `adapter-host` also knows `spi`; the core does not know `spi`.
ArchUnit tests additionally check the same rules at package level.
xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015] gives the reasons
for modules instead of a package convention.

=== Context

Issue #1 asks for DDD and hexagonal or Clean Architecture. The owner confirmed
the SPI approach for domain data, authorization through the host's Spring
Security, and no multi-tenancy. The host application decides the deletion and
retention rules.

=== Decision Drivers

* Replaceability of rendering, storage and database.
* Testability of the core without a Spring context.
* A clear, stable integration boundary to the host.

=== Considered Options

==== Option 1: Hexagonal with SPI ports for data, permission and deletion

The host implements narrow interfaces. The library fetches data itself when it
creates a preview.

==== Option 2: Hexagonal, the host passes a data object with every call

Less coupling to host interfaces, but every caller must know the matching data
context and send it along; the React frontend would need domain knowledge.

==== Option 3: Classic layered architecture with Spring everywhere

Less structure, quick start; violates the requirement from the issue and makes
replacement and isolated testing harder.

=== Consequences

==== Positive

* Domain and use cases can be tested with JUnit 5 and Mockito without Spring.
* Host-specific rules (permission, deletion) stay with the host.

==== Negative

* More modules and mapping code than with a layered architecture.
* The SPIs are public API; changes need versioning.

==== Neutral or Follow-Up

* Record the module cut in ADR-009 (monorepo).
* Prove the SPI contracts with a sample implementation in the sample
  application.
