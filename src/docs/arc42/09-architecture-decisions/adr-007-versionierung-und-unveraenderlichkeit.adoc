[[adr-007-versionierung-und-unveraenderlichkeit]]
== ADR-007: Versioned templates and immutable letters

=== Status

Proposed.

This ADR was created with AI assistance. It counts as an architecture decision
only once the responsible owner has reviewed and accepted it.

=== Decision

We propose:

* Letterheads and letter templates have **versions** with the state *draft*,
  *published* or *withdrawn*. Published versions are immutable;
  changes create a new version. At most one version per template is
  published; the previous one is then *superseded*; addendum of 2026-11-22,
  see xref:adr-022-eine-veroeffentlichte-version-je-vorlage[ADR-022].
* A **stored letter** stores the generated PDF, a SHA-256 checksum
  and the IDs of the template versions used. It is **never rendered again**.
* The **preview** creates a short-lived **data state (snapshot)**. Saving
  renders the PDF from exactly this snapshot, so that what is stored matches the
  preview, even if domain data has changed in the meantime.
* The snapshot is bound to the **user**, the **business reference** and **both
  template versions** (letterhead and letter template). On saving, the
  permission to create is checked again through the host. A corrected
  template requires a new preview.
* The snapshot stores a **hash (SHA-256) of the formatted
  data context**. On saving, the library reads the data context again together
  with the authorization check and compares the hash. If it differs, the letter
  is **not saved**. The UI reports the data change and asks for
  “Aktualisieren”. Rendering always uses the snapshot.
* A snapshot **expires after 30 minutes**. An expired snapshot is
  deleted. A cleanup runs for this at a short interval (for example every
  minute). Until then it is treated like one that does not exist. “Aktualisieren”
  or a reload creates a new preview with a new snapshot. The replaced
  snapshot is deleted in the same step.
* Whether a letter is deleted is decided by the host's `DeletionPolicy` (ADR-002).

=== Context

The owner has confirmed: templates are versioned, the stored PDF stays
unchanged. The host application decides the rules for deletion and retention.

On the snapshot and data changes, the owner confirmed on 2026-11-15
(Q-PO-011): the stored letter matches the preview exactly. Changed
data is detected and forces a refresh. The expiry time is
30 minutes. Expired and replaced snapshots are deleted immediately.

=== Decision Drivers

* Traceability: what the user has seen is stored.
* Immutability of stored letters.
* A simple model for business users (draft, published).

=== Considered Options

==== Option 1: Versioned templates, PDF unchanged, saving from the preview snapshot

What is stored matches the preview exactly. The snapshot must be kept for a short time.

==== Option 2: Versioned templates, saving reads the data again

No snapshot needed. What is stored can differ from the preview.

==== Option 3: No versioning, PDF unchanged

Simple, but it cannot be traced which template a letter was created with;
ongoing editing affects other users' previews.

=== Pugh Matrix

=== Consequences

==== Positive

* Stored letters are traceable in an audit-proof way.

==== Negative

* Managing snapshots (expiry time, storage location, cleanup) is additional effort.
* Saving needs an additional call to the host to read the data context again.
* If data changes often, the user has to refresh more often.

==== Neutral or Follow-Up

* Add the error case “data changed” to the runtime view (done).
