[[adr-009-build-monorepo-und-versionen]]
== ADR-009: Monorepo, Gradle und aktuelle Plattformversionen

=== Status

Vorgeschlagen (proposed).

Dieser ADR ist KI-gestützt entstanden. Er gilt erst als Architekturentscheidung,
wenn der verantwortliche Owner ihn geprüft und akzeptiert hat.

=== Entscheidung

Wir schlagen vor:

* **Monorepo**. Alle Quellen liegen unter `src/`, getrennt nach Art:
** `src/application/backend/` – Gradle-Multiprojekt (Kotlin DSL), geschnitten nach
   ADR-002:
*** `domaene`
*** `usecases/in` (eingehende Ports), `usecases/out` (ausgehende Ports, SPI) und
    `usecases/service` (Implementierung der Anwendungsfälle) als drei Module
*** `adapter/in/adapter-web`, `adapter/out/adapter-rendering`,
    `adapter/out/adapter-persistenz-jdbc`
*** `spring-boot-starter` und das Testmodul `architekturtests`
** `src/application/frontend/` – npm-Workspace mit dem Paket der React-Komponenten
   (TypeScript, Vite, UnoCSS).
** `src/docs/` – Architekturdokumentation, `src/examples/` – Beispielvorlagen (DOCX).
** `src/beispiel/` – Beispiel-Host-Anwendung (Spring Boot und React), sobald
   Anwendungsfälle gefunden sind.
* **Modulgrenzen erzwingen die Abhängigkeitsrichtung beim Kompilieren.** Ein
  eingehender Adapter hängt nur an `usecases/in`, ein ausgehender nur an
  `usecases/out`. Eine falsche Abhängigkeit scheitert damit schon am Compiler,
  ArchUnit prüft dieselben Regeln zusätzlich auf Paketebene. Der Host braucht für
  seine SPI-Implementierungen nur das kleine Artefakt `usecases-out`. Die
  Abwägung gegen Paketkonvention, Sichtbarkeit und JPMS steht in
  xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015].
* Die Gradle-Projekte sind flach benannt (`usecases-in`, `adapter-web`, …) und
  zeigen auf ihr Verzeichnis. Die Gruppenordner `adapter/in`, `adapter/out` und
  `usecases` sind keine eigenen Gradle-Projekte.
* **Versionen**: die **aktuelle stabile Spring-Boot-Version (4.x)**, entwickelt und
  getestet mit **Java 25 (LTS)**, kompiliert mit `--release 21`, damit Hosts auf
  Java 21 die Bibliothek nutzen können. Die genauen Patch-Versionen werden beim
  Anlegen des Builds festgelegt.
* **ArchUnit** prüft die hexagonalen Abhängigkeitsregeln, **Testcontainers** die
  Persistenz gegen echte Datenbanken.

Stand beim Anlegen des Gerüsts (#12): Gradle 9.9.1 (Wrapper), Spring Boot 4.1.2
(BOM; 4.2 war nur als Release Candidate verfügbar), ArchUnit 1.5.1, JaCoCo 0.8.16.
Die gemeinsamen Konventionen stehen im Convention-Plugin `standardschreiben.java-modul`
(`gradle/build-logic`). Jedes Modul bindet es ausdrücklich ein; es gibt keine
Konfiguration über `subprojects {}`. So bekommt nur ein Modul die Java-Regeln, das sie
anfordert, und die Konfiguration bleibt mit dem Configuration-Cache verträglich.
Der Workflow `backend.yml` baut mit dem Wrapper auf Java 21 (Baseline). Die
Matrix mit Java 21 und Java 25 wird mit #14 eingerichtet.

Antwort auf die Frage des Owners „Warum nicht die neueste Spring-Boot-Version?“:
Der ursprüngliche Vorschlag 3.x war Vorsicht wegen der Kompatibilität mit Hosts.
Ein Starter ist an die Spring-Boot-Hauptversion des Hosts gebunden. Da noch keine
Bestands-Hosts feststehen und ältere Linien aus der freien Unterstützung fallen,
ist die neueste stabile Version die bessere Wahl.

=== Kontext

Owner bestätigt Gradle mit Kotlin DSL, Monorepo, ArchUnit und Testcontainers und
fragt, warum nicht die neueste Spring-Boot-Version gewählt wird.

=== Entscheidungstreiber

* Lange Unterstützung der Plattform.
* Breite Nutzbarkeit in Hosts.
* Ein Repository für Backend, Frontend, Beispiel und Doku.

=== Betrachtete Optionen

==== Option 1: Spring Boot 4.x, Java 25 mit Ziel 21, Monorepo

Lange Unterstützung, modernste Plattform. Hosts auf Spring Boot 3 sind ausgeschlossen.

==== Option 2: Spring Boot 3.x, Java 21, Monorepo

Breiter kompatibel mit bestehenden Hosts, aber kürzere verbleibende Unterstützung
und baldiger Migrationsaufwand.

==== Option 3: Spring Boot 4.x, getrennte Repositories für Backend und Frontend

Unabhängige Releases, aber API-Änderungen über Repository-Grenzen hinweg schwerer
abzustimmen, Doku verstreut.

=== Pugh-Matrix

`+1` steht für bessere Unterstützung, `0` für neutral, `-1` für schwächere
Unterstützung und `?` für eine Bewertung, die eine menschliche Prüfung oder
einen Prototyp braucht. Enthält eine Spalte ein `?`, ist ihre Summe ebenfalls `?`.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Kriterium | Option 1 | Option 2 | Option 3
| Lange Unterstützung | +1 | -1 | +1
| Breite Nutzbarkeit in Hosts | 0 | +1 | 0
| Ein Repository | +1 | +1 | -1
s| Summe s| +2 s| +1 s| 0
|===

=== Konsequenzen

==== Positiv

* Keine absehbare Migration einer Hauptversion während des MVP.

==== Negativ

* Hosts auf Spring Boot 3 können die Bibliothek nicht nutzen (R-007).

==== Neutral oder Folgearbeiten

* Bei Bedarf eines Hosts auf Spring Boot 3: eigene Kompatibilitätslinie bewerten.
