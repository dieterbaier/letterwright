[[adr-009-build-monorepo-und-versionen]]
== ADR-009: Monorepo, Gradle and current platform versions

=== Status

Accepted on 2026-11-17.

This ADR was created with AI assistance. The owner reviewed and accepted it in
the review of PR #28.

=== Decision

We decide:

* **Monorepo**. All sources live under `src/`, separated by kind:
** `src/application/backend/` – Gradle multi-project (Kotlin DSL), cut according to
   ADR-002:
*** `domain/model` (domain model) and `domain/service` (domain services) as
    two modules; at compile time, domain services sees only `usecases/service`
*** `usecases/in` (inbound ports), `usecases/out` (outbound ports) and
    `usecases/service` (implementation of the use cases) as three modules
*** `spi` (interface to the host application with its own data types, ADR-016)
*** `adapter/in/adapter-web`, `adapter/out/adapter-rendering`,
    `adapter/out/adapter-persistence-jdbc`, `adapter/out/adapter-host`
*** `spring-boot-starter` and the test module `architecture-tests`
** `src/application/frontend/` – npm workspace with the package of the React components
   (TypeScript, Vite, UnoCSS).
** `src/docs/` – architecture documentation, `src/examples/` – sample templates (DOCX).
** `src/example/` – sample host application (Spring Boot and React), as soon as
   use cases are found.
* **Module boundaries enforce the dependency direction at compile time.** An
  inbound adapter depends only on `usecases/in`, an outbound one only on
  `usecases/out`; `adapter-host` also on `spi`. A wrong dependency therefore already fails at the compiler;
  ArchUnit additionally checks package rules from ADR-002. For compiling, the
  host gets only `spi`, even if it includes the starter (addendum
  2026-11-24: since xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]
  `spi` and `api`). The starter brings ports,
  use cases, domain and adapters only at runtime
  (xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]). The
  trade-off against a package convention, visibility and JPMS is in
  xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015].
* The Gradle projects have flat names (`domain-model`, `usecases-in`,
  `adapter-web`, …) and point to their directory. The group folders `domain`,
  `adapter/in`, `adapter/out` and `usecases` are not Gradle projects of their own.
* **Versions**: the **current stable Spring Boot version (4.x)**, developed and
  tested with **Java 25 (LTS)**, compiled with `--release 21`, so that hosts on
  Java 21 can use the library. The exact patch versions are set when the
  build is created.
* **ArchUnit** checks the hexagonal dependency rules, **Testcontainers** the
  persistence against real databases.

State when the scaffold was created (#12): Gradle 9.9.1 (wrapper), Spring Boot 4.1.2
(BOM; 4.2 was only available as a release candidate), ArchUnit 1.5.1, JaCoCo 0.8.16.
With #19, JSpecify 1.0.1 was added, kept in the version catalog independently of the
Spring Boot BOM (xref:adr-015-durchsetzung-der-modulgrenzen-im-backend[ADR-015]).
The shared conventions are in the convention plugin `letterwright.java-module`
(`gradle/build-logic`). Each module applies it explicitly; there is no
configuration via `subprojects {}`. This way only a module that asks for the Java
rules gets them, and the configuration stays compatible with the configuration cache.
The workflow `build.yml` builds the backend with the wrapper on Java 21 (baseline)
and Java 25 (#14).

State when the frontend scaffold was created (#13): Node.js `^22.22.2 || ^24.15.0 ||
>=26.0.0`, the intersection of the ranges of jsdom and Vitest. `engine-strict`
makes `npm ci` fail with a different version. In addition Vite 8.3,
Vitest 5.1 with V8 coverage, React 19.3 (peer dependency), UnoCSS 66.13,
axe-core 4.14, ESLint 10 with typescript-eslint 8.72. TypeScript stays at 6.0
because typescript-eslint does not yet support TypeScript 7. The package is named
`@dieterbaier/letterwright` and lives under
`src/application/frontend/packages/components`. The exact versions are in
`package-lock.json`.

Answer to the owner's question “Why not the newest Spring Boot version?”:
The original proposal 3.x was caution about compatibility with hosts.
A starter is bound to the host's Spring Boot major version. Since no
existing hosts are known yet and older lines drop out of free support,
the newest stable version is the better choice.

=== Context

The owner confirms Gradle with Kotlin DSL, monorepo, ArchUnit and Testcontainers and
asks why the newest Spring Boot version is not chosen.

=== Decision Drivers

* Long support of the platform.
* Broad usability in hosts.
* One repository for backend, frontend, sample and docs.

=== Considered Options

==== Option 1: Spring Boot 4.x, Java 25 with target 21, monorepo

Long support, the most modern platform. Hosts on Spring Boot 3 are excluded.

==== Option 2: Spring Boot 3.x, Java 21, monorepo

More broadly compatible with existing hosts, but shorter remaining support
and migration effort soon.

==== Option 3: Spring Boot 4.x, separate repositories for backend and frontend

Independent releases, but API changes across repository boundaries are harder
to coordinate, docs scattered.

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker
support and `?` a rating that needs human review or
a prototype. If a column contains a `?`, its sum is `?` as well.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Long support | +1 | -1 | +1
| Broad usability in hosts | 0 | +1 | 0
| One repository | +1 | +1 | -1
s| Sum s| +2 s| +1 s| 0
|===

=== Consequences

==== Positive

* No foreseeable migration of a major version during the MVP.

==== Negative

* Hosts on Spring Boot 3 cannot use the library (R-007).

==== Neutral or Follow-Up

* If a host on Spring Boot 3 needs it: assess a separate compatibility line.
