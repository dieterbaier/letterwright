== ADR-018: DDD roles and self-validation in the domain model

=== Status

Accepted on 2026-11-21.

The owner made the four individual decisions on 2026-11-21 after the review of
PR #57: jMolecules annotations, the version as part of the template, equality
by identity, and empty content only in the draft. The ADR was worded with AI
assistance; the owner accepted it in the review of PR #57.

=== Decision

* **DDD roles with jMolecules annotations.** The domain uses only the artifact
  `org.jmolecules:jmolecules-ddd` with `@AggregateRoot`, `@Entity`,
  `@ValueObject` and `@Identity`. It contains only annotations and interfaces
  and depends only on `jstereotype`, which also contains only annotations. The
  class names stay Ubiquitous Language, so `Letterhead` and not
  `LetterheadAggregate`. Integrations of jMolecules (Spring, Jackson,
  ByteBuddy) and its ArchUnit rules are therefore not permitted.
* **Aggregates.**
** `Letterhead` and `LetterTemplate` are aggregate roots over their
   versions. `TemplateVersion` is an entity in its aggregate. Every change to a
   version goes through the root. The root secures the rules across all
   versions: the numbers run from 1 without gaps, there is at most one draft,
   and it is the newest version.
** `Snapshot` and `Letter` are separate aggregates. They refer to template
   versions only via `VersionReference`, and the letter template refers to its
   letterhead only by ID.
* **Equality.** Aggregates and entities are final classes and equal by their
  identity. Two states of the same letterhead are therefore equal. Value
  objects are records, enums or immutable classes with value equality. The
  identity is marked with `@Identity`: for the aggregates the ID field, for
  `TemplateVersion` the method `reference()`, which returns template and number.
* **Self-validation.**
** Every type checks every required attribute in the constructor, composite
   types too. That a contained value object checks itself does not replace the
   check whether it is present.
** The general checks are in the module `validation`: required value, not
   empty, not blank, lower bound, collection without gaps. It is framework-free
   and knows no other module.
** The type itself decides which check applies to an attribute. Business rules
   such as state transitions stay in the model.
* **Error contract.**
** An invalid or missing value results in `ValidationException` (an
   `IllegalArgumentException`) whose message names the attribute. Never a
   `NullPointerException`.
** A step that is forbidden by the business rules results in
   `IllegalStateTransition` (an `IllegalStateException`), for example changing
   a published version.
* **Creation.**
** New objects are created through descriptive factory methods such as
   `create`, `fromSnapshot` and `generate()`.
** Stored objects are created through `restore`. All checks apply there
   too.
* **Time as a parameter.** The model reads no clock. The use case reads its
  clock once and passes the point in time.
* **Empty content.** A draft may have empty content, but not missing content.
  Publishing requires content that does not consist only of whitespace.

ArchUnit checks that, apart from the JDK, the domain uses only JSpecify, the
jMolecules annotations and `validation`. It also checks that `validation`
knows no other package of the library. The SPI does not use `validation`; it
stays self-contained according to ADR-016.

=== Context

The review of PR #57 showed that the first domain model allowed invalid
objects. `new Letterhead(null, "Name", null)` was possible, and a missing text
resulted in a `NullPointerException` instead of an understandable message.
Records compared all components, so two states of the same letterhead were
unequal. No object could ensure that each version number is assigned only once.

The owner wants to recognize the DDD roles in the code and to have the general
checks in a separate module. ADR-002 records which libraries the domain may
use.

=== Decision Drivers

* Ubiquitous Language: the names in the code are the terms of the glossary.
* No invalid model object; errors where they arise.
* Invariants across several objects are in the model, not in the use case.
* As few and as small dependencies in the domain as possible.

=== Considered Options

==== Option 1: Naming convention

Suffixes such as `…Aggregate`, `…Entity` and `…Value`, with documented variants
such as `…Id` and `…Reference`. No dependency, but technical names in the code and
in the glossary.

==== Option 2: jMolecules annotations (chosen)

Standardized annotations; names stay domain names. A small dependency made only
of annotations. The ArchUnit rules of jMolecules can be used later if there is
a reason.

==== Option 3: Role only in the glossary

No change to the code; the role is stated in the glossary. Nothing checks
whether code and glossary match.

=== Pugh Matrix

`+1` means better support, `0` neutral and `-1` weaker support. The matrix is
unweighted.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Role recognizable in the code | +1 | +1 | -1
| Names stay Ubiquitous Language | -1 | +1 | +1
| No additional dependency | +1 | -1 | +1
| Can be checked automatically later | 0 | +1 | -1
s| Sum s| +1 s| +2 s| 0
|===

Self-validation, aggregate boundaries and equality are the same with every
option. The matrix compares only the marking.

=== Consequences

==== Positive

* A model object is always valid. Whoever creates it gets an error with the
  attribute name instead of a later `NullPointerException`.
* The aggregate secures the rules across all versions of a template. The use
  case and the persistence do not have to rebuild them.
* The roles are visible in the code; the names stay domain names.

==== Negative

* A template is loaded with all its versions. With many versions this can
  become expensive; then a separate aggregate for the version would have to be
  reassessed.
* Aggregates are classes with hand-written `equals`, `hashCode` and accessors
  instead of records.
* An additional dependency in the domain that has to be checked as well on
  updates.

==== Neutral or Follow-Up

* ADR-002 records which libraries the domain may use. The version of
  2026-11-21 comes from the review of PR #57.
* The crosscutting concept “Domain Model” describes the conventions for new
  types.
* The persistence (#6) restores aggregates via `restore`. It handles concurrent
  changes to the same template, for example with a version column.
* #55 determines whether there may be further valid versions besides the newest
  published version. The model allows several published versions.
  Addendum 2026-11-22: at most one, decided in
  xref:adr-022-eine-veroeffentlichte-version-je-vorlage[ADR-022].
