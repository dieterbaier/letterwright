[[adr-010-frontend-tests-mit-vitest]]
== ADR-010: Frontend-Tests mit Vitest statt Jest

=== Status

Angenommen (accepted) am 2026-11-18.

Dieser ADR ist KI-gestützt entstanden. Der Owner hat ihn bei der Prüfung von
Epic #4 angenommen (Issue #37).

=== Entscheidung

Wir schlagen **Vitest** mit **React Testing Library**, **jsdom** und
**vitest-axe** bzw. axe-core vor. Die Abdeckung misst Vitest mit dem V8-Provider.

=== Kontext

Das Issue nennt „Nest“; gemeint war Jest. Der Owner akzeptiert Vitest, verlangt aber
eine Begründung per ADR. Gebaut wird mit Vite.

=== Entscheidungstreiber

* Gleiche Transformations-Pipeline in Build und Test (TypeScript, UnoCSS, ESM).
* Jest-kompatible API, geringe Einarbeitung.
* Geschwindigkeit und Wartungsaufwand der Konfiguration.

=== Betrachtete Optionen

==== Option 1: Vitest

Nutzt `vite.config.ts` direkt, native ESM- und TypeScript-Unterstützung, Jest-kompatible
API (`describe`, `it`, `expect`, `vi.fn` statt `jest.fn`).

==== Option 2: Jest

Sehr verbreitet. Braucht eigene Transformation (ts-jest oder Babel), ESM-Unterstützung
ist experimentell, Vite-Plugins (UnoCSS) müssen separat nachgebildet werden.

==== Option 3: Jest mit vite-jest-Brücke

Behält Jest, nutzt teilweise die Vite-Pipeline. Zusätzliche, wenig gepflegte
Abhängigkeit.

=== Pugh-Matrix

`+1` steht für bessere Unterstützung, `0` für neutral, `-1` für schwächere
Unterstützung und `?` für eine Bewertung, die eine menschliche Prüfung oder
einen Prototyp braucht. Enthält eine Spalte ein `?`, ist ihre Summe ebenfalls `?`.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Kriterium | Option 1 | Option 2 | Option 3
| Gleiche Pipeline wie der Build | +1 | -1 | 0
| Jest-kompatible API | +1 | +1 | +1
| Geringer Konfigurationsaufwand | +1 | -1 | -1
s| Summe s| +3 s| -1 s| 0
|===

=== Konsequenzen

==== Positiv

* Keine doppelte Build-Konfiguration für Tests.

==== Negativ

* Einige Jest-spezifische Plugins sind nicht direkt nutzbar.

==== Neutral oder Folgearbeiten

* Testkonventionen im Frontend-README festhalten.
