== ADR-010: Frontend tests with Vitest instead of Jest

=== Status

Accepted on 2026-11-18.

This ADR was created with AI assistance. The owner accepted it when reviewing
Epic #4 (issue #37), together with its outgoing relations.

=== Decision

We use **Vitest** with **React Testing Library**, **jsdom** and
**vitest-axe** or axe-core. Vitest measures coverage with the V8 provider.

=== Context

The issue says “Nest”; Jest was meant. The owner accepts Vitest, but asks for
a justification in an ADR. The build uses Vite.

=== Decision Drivers

* The same transformation pipeline in build and test (TypeScript, UnoCSS, ESM).
* Jest-compatible API, little ramp-up.
* Speed and maintenance effort of the configuration.

=== Considered Options

==== Option 1: Vitest

Uses `vite.config.ts` directly, native ESM and TypeScript support, Jest-compatible
API (`describe`, `it`, `expect`, `vi.fn` instead of `jest.fn`).

==== Option 2: Jest

Very widespread. Needs its own transformation (ts-jest or Babel), ESM support
is experimental, Vite plugins (UnoCSS) must be reproduced separately.

==== Option 3: Jest with the vite-jest bridge

Keeps Jest, partly uses the Vite pipeline. An additional, poorly maintained
dependency.

=== Pugh Matrix

`+1` means better support, `0` neutral, `-1` weaker
support and `?` a rating that needs human review or
a prototype. If a column contains a `?`, its sum is `?` as well.

[.pugh-matrix]
[cols="2,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3
| Same pipeline as the build | +1 | -1 | 0
| Jest-compatible API | +1 | +1 | +1
| Low configuration effort | +1 | -1 | -1
s| Sum s| +3 s| -1 s| 0
|===

=== Consequences

==== Positive

* No duplicate build configuration for tests.

==== Negative

* Some Jest-specific plugins cannot be used directly.

==== Neutral or Follow-Up

* Record test conventions in the frontend README.
