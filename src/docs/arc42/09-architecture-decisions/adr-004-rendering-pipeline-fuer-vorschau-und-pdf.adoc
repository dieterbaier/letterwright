[[adr-004-rendering-pipeline-fuer-vorschau-und-pdf]]
== ADR-004: Rendering pipeline for preview and PDF

=== Status

Accepted on 2026-11-21.

This ADR was created with AI assistance. The owner reviewed and accepted it
after the prototype (#3). The PDF/UA spot check and the test with NVDA were
carried out on 2026-11-23 (owner); the classification of two warnings from
axesCheck is still open (see Result of the prototype).

=== Decision

We propose a two-stage pipeline:

. **Merge** (backend): the template version (letterhead and letter template)
  and the data context are merged with the placeholder language (ADR-008) into
  **one complete HTML document** with Paged Media CSS.
. **Output**:
** **Preview**: the HTML is delivered to the frontend and paginated there with
   **Paged.js** (MIT), including page numbers. The owner has already used
   Paged.js successfully.
** **PDF**: the same HTML is rendered in the backend with **openhtmltopdf**
   (LGPL, based on Apache PDFBox), which supports CSS Paged Media, PDF/A and
   PDF/UA.

=== Acceptance criteria for the prototype

Every option that is to be chosen must prove all of the following criteria for
**the same reference letters** (DOCX specifications supplied later,
single-page and multi-page):

* PDF/A-2b without veraPDF errors (xref:qs-001-pdfa-konformitaet[QS-001]).
* PDF/UA-1 without veraPDF errors and a passed manual spot check
  (xref:qs-002-barrierefreies-pdf[QS-002]).
* Accessible paginated preview: check of the rendered preview on the multi-page
  reference letter according to xref:qs-003-barrierefreie-vorschau[QS-003], automatically (axe-core,
  keyboard) and manually with a screen reader (reading order, repeated headers
  and footers, focus, status messages). The result feeds into the decision.
* Fidelity between preview and PDF (xref:qs-004-wiedergabetreue-vorschau-und-pdf[QS-004]).
* Style fidelity to the central DOCX specification (xref:qs-013-stiltreue-zur-zentralen-docx-vorgabe[QS-013]).

Option 1 is accepted only if it meets all criteria. **Option 2 is not a secured
fallback**, but a candidate: it is checked against the same criteria in the
spike if option 1 fails. In particular, it is open whether a PDF created by
Chromium and post-processed with PDFBox meets PDF/UA-1.

=== Context

Preview and saved document shall look the same. The preview may be HTML.
Commercial tools and iText (AGPL) are excluded. Thymeleaf and Apache FOP would
be fine for the owner; openhtmltopdf is unknown to him and shall be assessed in
an ADR.

=== Decision Drivers

* Identical look of preview and PDF.
* PDF/A and PDF/UA without commercial tools.
* Accessible HTML preview.
* Few runtime dependencies in the host (no external processes).

=== Considered Options

==== Option 1: Paged.js for the preview, openhtmltopdf for the PDF (same HTML)

Lightweight, purely JVM-based in the backend, PDF/A and PDF/UA built in. Two
layout engines can differ in details (hyphenation, font metrics, line and page
breaking rules).

==== Option 2: Paged.js in headless Chromium for preview and PDF, PDF/A post-processing with PDFBox

One engine, highest fidelity. Requires Chromium as a runtime dependency in the
host. Chromium does not create PDF/A; the post-processing (XMP, OutputIntent,
font embedding) is separate, risky effort. Whether the result also meets
PDF/UA-1 (tagging from Chromium, preserved after the post-processing) is not
proven. A candidate until the acceptance criteria are proven.

==== Option 3: Apache FOP (XSL-FO) for the PDF, separate XSLT transformation for the HTML preview

Very mature for PDF/A and tagged PDF. Preview and PDF are created by different
transformations, differences are likely; does not fit ADR-003.

*Fallback* (owner, 2026-11-21): Customers usually accept Apache FOP with an
XSLT transformation. If a customer does not accept openhtmltopdf, option 3
becomes an option again. For this library the owner does not choose it for
now; it is too heavyweight for him. A switch would affect the port `Renderer`
and the template format (ADR-003): preview and PDF would no longer be created
from the same HTML, and QS-004 would have to be proven again (R-003).

==== Option 4: The preview shows the generated PDF (pdf.js)

Exactly identical, but the preview is less accessible to assistive
technologies, and every preview costs a complete PDF generation.

=== Pugh Matrix

`+1` stands for better support, `0` for neutral, `-1` for weaker support and
`?` for a rating that needs human review or a prototype. If a column contains a
`?`, its sum is `?` as well.

[.pugh-matrix]
[cols="2,1,1,1,1", options="header"]
|===
| Criterion | Option 1 | Option 2 | Option 3 | Option 4
| Identical look | ? | +1 | -1 | +1
| PDF/A and PDF/UA without commercial tools | +1 | ? | +1 | +1
| Accessible HTML preview | +1 | +1 | +1 | -1
| Few runtime dependencies | +1 | -1 | +1 | +1
| Response time of the preview | +1 | 0 | 0 | -1
s| Sum s| ? s| ? s| +2 s| +1
|===

Option 4 is ruled out regardless of its sum, because it violates the mandatory
requirement of an accessible preview. Option 3 has the best certain sum, but it
misses the most important goal, an identical look, and does not fit the
template format from ADR-003. Whether option 1 beats it is decided by the
fidelity measurement in the prototype.

=== Consequences

==== Positive

* No external processes; the PDF is created in the host's JVM.
* The owner's experience with Paged.js is used.

==== Negative

* Fidelity must be tested actively (R-002).
* Dependency on a community project (R-003); LGPL is compatible with MIT as a dependency, but must be stated in the license documentation.
* Customers can reject openhtmltopdf. Then option 3 would be the fallback, at the price described above.

==== Neutral or Follow-Up

* Prototype together with ADR-003: done for option 1, result above. Option 2 is postponed (owner's decision).
* The PDFBox post-processing of the footer must be checked with every update of openhtmltopdf (R-003).
* Fonts: the font of the central DOCX specification is authoritative (QS-013). Both engines load **the same file** (openhtmltopdf embedded in the PDF, Paged.js via `@font-face` from the backend). xref:adr-017-bereitstellung-der-schriften[ADR-017] governs where the file comes from: the host provides fonts that require a license in a configurable folder; otherwise a free substitute font of the library applies. The spike checks both paths separately (Q-PO-010): (1) *Reference fonts from the host:* they load in the sandboxed iframe under the intended CSP (ADR-014), openhtmltopdf embeds them in the PDF, and their license permits both uses, embedding in the PDF and delivery as a web font. (2) *Free substitute fonts:* preview and PDF are measured against QS-004 and QS-013. A successful path 2 does not replace the proof for path 1.


=== Result of the prototype

The throwaway prototype from #3 (`prototyp/README.adoc`) checked option 1 on
both reference letters. Status of the acceptance criteria:

[cols="2,1,4", options="header"]
|===
| Criterion | Status | Finding
| PDF/A-2b (QS-001) | met | veraPDF without violations, also with substitute fonts and for a malicious test letter.
| PDF/UA-1 (QS-002) | partially | veraPDF without violations. Manual spot check on both reference PDFs (owner, 2026-11-23): NVDA with Acrobat Reader without findings; axesCheck reports PDF/UA and WCAG as met, with one warning each without details (structure tree, WCAG 4.1), which is not yet classified. The content footer only becomes readable through a post-processing step with PDFBox (see below).
| Accessible preview (QS-003) | with limits | axe-core without violations of the levels serious and critical, no focus trap, status messages via `aria-live`. VoiceOver reads the letter completely, but at the end of the first page it needs a new entry into the frame. At 200 % zoom the preview scrolls instead of reflowing. NVDA with Chrome reads the letter completely, including the alternative texts; order and repetitions are not recorded individually with NVDA.
| Fidelity (QS-004) | met, measurement follows | The Chrome print PDF of the preview differs from the PDF by at most 0.3 mm, with the same number of pages and the same first and last line on each page. In the owner's visual check on screen (100 %, side by side) no difference can be seen. The exact measurement of the screen rendering will be an automated test in #7.
| Style fidelity (QS-013) | assumed | The PDF differs from the Word PDF by at most 0.1 mm. An acceptance by the central department is not possible; the project assumes that the style fidelity is right (owner, 2026-11-21).
|===

*Footer in the PDF.* openhtmltopdf always outputs running elements as
artifacts; there is no setting for this. As flowing content of the first page,
it pushes the footer to the next page. A post-processing step with PDFBox
therefore tags the content footer as paragraphs at the end of the structure
tree. On every generation it is checked that exactly the footer texts from the
HTML are there in this order; otherwise the generation aborts.

*Owner's decisions* in the https://github.com/dieterbaier/standardschreiben/pull/47#pullrequestreview-5997431593[review of PR #47]:

* *Chromium (option 2) is not checked for now.* A different PDF renderer does
  not remove the limits of the Paged.js preview. The deviations stay open.
  Option 2 becomes an option again if the PDF/UA spot check shows a problem
  that cannot be solved reliably with openhtmltopdf and PDFBox.
* *The PDFBox post-processing is accepted* as long as it and its fallback are
  documented. The proof stays active on every generation. Fallback: the footer
  as a regular, tagged block in the letter layout; a changed placement needs
  acceptance according to QS-013.
* The preview may scroll instead of reflowing at 200 % zoom. The project does
  not pursue the effort for VoiceOver at the page change any further (owner,
  2026-11-20).

*Fonts.* Path 1: Arial and Arial Narrow from the font folder load in the
sandboxed iframe under the CSP, and openhtmltopdf embeds them. On the license,
the owner decided on 2026-11-21: the library does not ship fonts that require a
license. If the host provides them, the PDF embeds subsets of them (PDF/A
requires this), and the preview receives them as a web font. The project
assumes that the host is allowed to do both; its license is authoritative.
Path 2: see xref:adr-017-bereitstellung-der-schriften[ADR-017].

*Further findings:* Preview and PDF are created from the same sanitized HTML
(xref:adr-014-isolation-der-vorschau-im-iframe[ADR-014]); the preview only gets
additions in the head. The preview of the finished PDF (option 4) would be
exactly identical, but stays ruled out for the reasons given. The prototype did
not check the maintenance status of openhtmltopdf (assumption below, R-003).

*Acceptance* (owner, 2026-11-21): Option 1 is accepted. QS-013 counts as an
assumption that the first real customer deployment must confirm; that is only
possible with a production-ready state. Fidelity on screen is confirmed by a
visual check and will be measured automatically in #7. The PDF/UA spot check
and the test with NVDA have been carried out (owner, 2026-11-23); the
classification of the two warnings from axesCheck is open and with the owner.
If the spot check shows a problem that cannot be solved reliably with
openhtmltopdf and PDFBox, option 2 becomes an option again.

=== Assumptions

* openhtmltopdf is developed further in an actively maintained community fork version. Checked on 2026-11-21: `io.github.openhtmltopdf`, release 1.1.114 of 2026-11-16; the repository `openhtmltopdf/openhtmltopdf` is not archived. The prototype uses this version.
* The layout requirements of letters are simple enough (no complex multi-column layout) that both engines break lines and pages the same way.

=== Open Questions

* None. On printing, the owner decided on 2026-11-16 (Q-PO-002): the preview
  is not printed. “Drucken” exists only for the saved letter, and what is
  printed is its PDF, through the browser's print function.
