== Save and Download a Letter

[plantuml,laufzeit-speichern,svg]
----

actor Clerk as SB
participant "Preview (React)" as UI
participant "adapter-web" as Web
participant "usecases-service" as App
participant "Host: AuthorizationCheck" as Host
participant "adapter-rendering" as Ren
participant "adapter-persistence-jdbc" as Per
SB -> UI: Save
UI -> Web: POST /letters (snapshot ID)
Web -> App: Save letter (snapshot ID)
App -> App: Load snapshot; does it belong to the logged-in user?\nHas it not expired yet?
App -> Host: May the user create from this letter template\nfor this reference? (ForCreation, again)
Host --> App: allowed
App -> App: Snapshot open? (consumed: return existing letter,\nwithout data context and without PDF)
App -> Host: Request data context (again)
Host --> App: Data context (formatted)
App -> App: Compare hash: unchanged
App -> Ren: Create PDF from snapshot\n(with the template versions fixed in the snapshot)
Ren --> App: PDF
App -> Ren: Check conformance (PDF/A-2b, PDF/UA-1)
Ren --> App: conformant
App -> App: Create letter from snapshot; snapshot is consumed
App -> Per: Store PDF; save letter and consumed snapshot\natomically, only if the snapshot is still open
App --> Web: Letter ID
Web --> UI: 201, download link
SB -> UI: Download
UI -> Web: GET /letters/{id}/pdf
Web -> App: Retrieve letter ({id})
App -> App: Load letter; visible?
App -> Host: May the user download for this reference? (ForLetter)
Host --> App: allowed
App -> Per: Read PDF
Per --> App: PDF
App -> App: Checksum equal to the one from saving?
App --> Web: PDF (unchanged)
Web --> UI: 200, PDF
@enduml
----

The preview takes the newest published versions of letter template and
letterhead. If the reference type does not match, the library does not ask the
host at all. It checks whether there are published versions only once it has
the permission; an unauthorized user always gets “not allowed”. Without
permission or without a published version, it does not ask the host for the
data context
(xref:adr-020-zulaessige-kombination-aus-standardschreiben-und-bezug[ADR-020]).
An updated preview creates a new snapshot, whose 30 minutes start anew, and
deletes the previous one if it belongs to the user and is still open. The
persistence checks whether it is open in the same step as the deletion. It
ignores a foreign or unknown previous snapshot, as if none had been given. The
behavior is specified in `features/letters/create-preview.feature`.

The snapshot is bound to the logged-in user, the business reference and both
template versions (letterhead and letter template). When saving, the library
checks the creation permission **again** through the host. If the permission
was revoked after the preview, nothing is saved. A snapshot of another user is
treated like a non-existent one (404).

At most one letter is created from a snapshot
(xref:adr-021-hoechstens-ein-schreiben-je-snapshot[ADR-021]). Saving consumes
the snapshot; after that it no longer holds a data context, only what a retry
needs. If the user saves the same preview again, for example after a double
click or because the response was lost, they get back the letter already saved,
without data being read or a PDF being created. If two requests save at the
same time, the persistence saves only the first; the other removes its PDF and
gets the letter of the first. If the outcome stays uncertain, nothing is rolled
back. A new letter is created only from a new preview. If the data context has
changed, no PDF is created; the snapshot stays open until a new preview
replaces it or it expires. A PDF that is not conformant or cannot be checked is
not saved (fail-closed). If the letter has meanwhile been hard or logically
deleted, a retry finds nothing anymore and gets “snapshot unknown”. The same
applies to a concurrent request whose snapshot is recognized as consumed only
after the deletion; it removes its PDF. The behavior is specified in
`features/letters/save-letter.feature`.

Downloading delivers the PDF only if its SHA-256 checksum matches the one from
saving
(xref:qs-008-unveraenderliche-schreiben[QS-008]). If it differs, the stored data
is defective: the download fails with a technical error instead of delivering a
changed PDF. A non-existent, a logically deleted and a not allowed letter are
all the same “unknown” for the user (404,
xref:qs-009-zugriffsschutz-beim-download[QS-009]). The behavior is specified in
`features/letters/download-letter.feature`.

----

The host grants the permission to view per reference. Without it the library
reads nothing and counts nothing; the list is “not allowed”. The persistence
filters out letters for other references and logically deleted ones in the
query, that is, before paginating and counting. Total count and number of pages
refer only to the visible letters
(xref:qs-009-zugriffsschutz-beim-download[QS-009]). The behavior is specified in
`features/letters/list-letters.feature`.

== Delete a Letter

[plantuml,laufzeit-loeschen,svg]
----
@startuml
actor Clerk as SB
participant "List (React)" as UI
participant "adapter-web" as Web
participant "usecases-service" as App
participant "Host: AuthorizationCheck" as Host
participant "Host: DeletionPolicy" as Richtlinie
participant "adapter-persistence-jdbc" as Per
SB -> UI: Delete
UI -> Web: DELETE /letters/{id}
Web -> App: Delete letter ({id})
App -> App: Load letter; visible?
App -> Host: May the user delete for this reference? (ForLetter)
Host --> App: allowed
App -> Richtlinie: How to delete? (DeletionRequest)
alt hard
  Richtlinie --> App: hard
  App -> Per: Remove letter, then remove PDF
else logical
  Richtlinie --> App: logical
  App -> Per: Save letter as logically deleted; PDF remains
else blocked
  Richtlinie --> App: blocked (reason)
end
App --> Web: deleted or blocked with reason
@enduml
----

The library asks the deletion policy only after the host has allowed the
deletion. A non-existent, an already logically deleted and a not allowed letter
are all the same “unknown” for the user; the deletion policy is then not asked.
When hard deleting, first the letter is removed, then its PDF: if removing the
PDF fails, a PDF without a letter remains instead of a letter without a PDF. A
logically deleted letter keeps its PDF, but appears in no list and can no
longer be downloaded. The behavior is specified in
`features/letters/delete-letter.feature`.

== Publish a Template Version

[plantuml,laufzeit-veroeffentlichen,svg]
----
@startuml
actor "Template manager" as VV
participant "Editor (React)" as UI
participant "adapter-web" as Web
participant "usecases-service" as App
participant "Host: AuthorizationCheck" as Host
participant "adapter-persistence-jdbc" as Per
participant "adapter-rendering" as Ren
VV -> UI: Publish
UI -> Web: POST /templates/{id}/publication
Web -> App: Publish template version ({id})
App -> Host: May the user publish? (PUBLISH)
Host --> App: allowed
App -> Per: Load template
Per --> App: Template with draft
alt Letter template
  App -> Per: Load letterhead
  Per --> App: published version of the letterhead
  App -> Ren: Proof PDF (letterhead, draft,\nsample data of both versions)
else Letterhead
  App -> Ren: Proof PDF (draft, built-in sample content,\nsample data)
end
Ren --> App: PDF
App -> Ren: Check PDF (PDF/A-2b, PDF/UA-1)
Ren --> App: conformant
App -> Per: Replace template, only if unchanged since loading:\ndraft published, previous version superseded
Per --> App: replaced
App --> Web: published (version)
@enduml
----

Publishing requires the template action `PUBLISH`; without it the library loads
nothing and renders nothing. Before publishing, a proof PDF is created with the
sample data of the version and checked with the same checker as every saved
letter
(xref:adr-005-pdfa-und-barrierefreiheit[ADR-005]). If it is not conformant, the
draft stays a draft, and the template manager receives the findings; if the
check cannot be run, nothing is published either. A letter template without a
published letterhead is not published. The persistence replaces the template
only if it is unchanged since loading; otherwise the library reports
“outdated”, and no unchecked content is published. This replacement does not
protect the letterhead of a letter template: if it is superseded or withdrawn
during the check, the time of the check counts, as if the letterhead had been
changed only afterwards. After that, the new version is the only published one,
and the previous one is superseded; saved letters keep their versions
(xref:adr-022-eine-veroeffentlichte-version-je-vorlage[ADR-022]).

Withdrawing works the same way, without a proof PDF: the published version is
withdrawn, and until the next publication no preview is created with the
template. The behavior is specified in
`features/templates/publish-template-version.feature` and
`features/templates/withdraw-template-version.feature`.

== Print a Saved Letter

Only a saved letter is printed (Q-PO-002). The preview does not offer
“Drucken”.

[plantuml,laufzeit-drucken,svg]
----
@startuml
actor Clerk as SB
participant "List (React)" as UI
participant "adapter-web" as Web
participant "usecases-service" as App
participant "Browser: print function" as Druck
SB -> UI: Print (saved letter)
UI -> Web: GET /letters/{id}/pdf
Web -> App: Retrieve letter ({id})
App -> App: Check permission (host)
App --> Web: PDF (unchanged)
Web --> UI: 200, PDF
UI -> Druck: Pass PDF to the browser's print function
@enduml
----

The same unchanged PDF as for the download is printed. If a user prints the
preview through the browser's print function, the library does not prevent
this. It is, however, not responsible for that result.

== Error Case: Permission Revoked When Saving

If the host refuses when saving, nothing is created and nothing is persisted.
The snapshot is discarded. The response reveals no content of the snapshot.

== Error Case: PDF Not Conformant, Rendering Fails or Check Cannot Be Run

If PDF generation fails, the PDF is not conformant, or the conformance check
cannot be run (error, timeout), **nothing is persisted** (fail-closed, see
xref:adr-005-pdfa-und-barrierefreiheit[ADR-005]). The user receives an
understandable message. The error is logged with template versions and
correlation ID, without personal content.

* If the cause lies in the template, the template manager must publish a **new
  template version**. The old snapshot stays bound to the faulty version; the
  user needs a **new preview** with the corrected version.
* In case of a temporary technical error (e.g. timeout), the user can retry
  saving with the same snapshot as long as it has not expired.

== Error Case: Data Changed Since the Preview

If the hash of the newly read data context differs from the hash in the
snapshot, nothing is created and nothing is persisted. The user interface
reports that the data has changed and requires “Aktualisieren”. This creates a new
preview with a new snapshot. The old snapshot is deleted in the process
(xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007]).

== Error Case: Snapshot Expired

A snapshot expires 30 minutes after the preview and is deleted. If it has
expired when saving, the library refuses the saving and asks for a new
preview, instead of saving with newly read data. Reloading the preview
creates a new snapshot
(xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007]).
