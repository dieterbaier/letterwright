= Crosscutting Concepts

== Threat Model

[cols="1,2,2", options="header"]
|===
| Threat | Attack vector | Countermeasure
| Template injection | A manipulated template executes code | Hardened FreeMarker configuration, tests (xref:r-004-template-injection-durch-vorlagen[R-004])
| Unauthorized access to letters | Guessed or foreign IDs | UUIDs, authorization check on every access, 404 instead of 403 (xref:qs-009-zugriffsschutz-beim-download[QS-009])
| Cross-site scripting | Placeholder values or template content with script | HTML escaping as default, HTML sanitizing of the editor content, no script in templates
| Malicious uploads | Manipulated logos (SVG with script) | Clean SVG or allow only raster formats, size limit
| Data leakage via logs | Personal data in the log | Log only IDs and versions
|===

== Security

Authentication and authorization come from the host's Spring Security. For
every action the library asks the SPI's `AuthorizationCheck`
(xref:adr-016-schnittstelle-zur-host-anwendung[ADR-016]). The
`AuthorizationRequest` has three kinds, and its type says which data it carries
(xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019],
xref:adr-020-zulaessige-kombination-aus-standardschreiben-und-bezug[ADR-020]):

* `ForTemplates` with a `TemplateAction` (`EDIT`, `PUBLISH`),
  without reference;
* `ForLetter` with a `LetterAction` (`VIEW`, `DOWNLOAD`,
  `DELETE`) and a business reference;
* `ForCreation` with a business reference and the letter template from which the
  letter is to be created.

Before the library asks the host about creating, it checks itself whether the
reference type of the letter template matches the reference. Only once it has
the permission does it check whether there are published versions, so that an
unauthorized user does not learn their state, and request the data context.
Whether a letter template exists and which reference type it belongs to, on the
other hand, stays distinguishable for unauthorized users as well. Editing and
publishing are separate so that the host can implement a four-eyes principle:
what is published goes into all new letters. Withdrawing belongs to publishing;
there is no deleting of templates, because versions are immutable
(xref:adr-007-versionierung-und-unveraenderlichkeit[ADR-007]).

If the host provides no `AuthorizationCheck` of its own, the starter's default
implementation applies. It allows a request if the logged-in user is the
requested one and has the authority `ROLE_LETTERWRIGHT_TEMPLATES_<ACTION>` or
`ROLE_LETTERWRIGHT_LETTERS_<ACTION>`, for example `ROLE_LETTERWRIGHT_LETTERS_CREATE` for
`ForCreation` (in Spring Security `roles("LETTERWRIGHT_LETTERS_CREATE")`). The host sets
different authorities with `letterwright.authorization.roles.templates.<ACTION>` and
`letterwright.authorization.roles.letters.<ACTION>`. Anonymous access does not
count as a login, even if Spring Security treats it as authenticated and its
authority (`ROLE_ANONYMOUS`) is mapped to an action. What is anonymous is
decided by an `AuthenticationTrustResolver` of the host if the host provides one
as a bean, otherwise by the one from Spring Security. The default
implementation does not evaluate the business reference and the letter
template. Whoever wants to make letters visible by reference (Q-PO-003)
provides a bean of their own; the default implementation then steps back.

== Testing

* Domain and application: JUnit 5 and Mockito, without Spring.
* Adapters: Testcontainers (PostgreSQL, MariaDB), Spring slice tests.
* Architecture: ArchUnit.
* Rendering: reference templates with veraPDF check and fidelity test.
* Frontend: Vitest, React Testing Library, axe-core; E2E with Playwright in the example application.
* Gate: 80 % line and branch coverage per module (xref:adr-011-qualitaetsgates-im-build[ADR-011]).

== Observability

Micrometer metrics for the duration of preview and PDF generation and the number
of failed conformance checks; structured logs with correlation ID,
without personal content. The metrics flow into the host's monitoring.

== Error Handling

A use case returns business errors (missing permission, expired snapshot,
non-conformant PDF) as a case of its result type, not as an exception
(xref:loesungsstrategie-code-stil[code style]). `adapter-web` maps every case;
they are passed to the frontend as RFC 9457 problem details and shown there in
an accessible way. Technical errors abort saving without persisting partial
results.

== Accessibility

Templates carry semantics (headings, lists, tables, alternative texts,
document language). The editor enforces alternative texts. The preview is HTML
with landmarks and keyboard operation; the PDF is tagged according to PDF/UA-1.

== Domain Model

xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018] defines the
conventions for types in the domain model:

* **Make the role visible.** Every type carries a jMolecules annotation:
  `@AggregateRoot`, `@Entity` or `@ValueObject`. The identity of an aggregate
  or entity is marked with `@Identity`, on the field or on the method that
  provides it. The name is the term from the
  glossary, without a technical suffix.
* **Equality.** Aggregates and entities are final classes, equal by their
  identity. Value objects are records, enums or immutable classes with
  value equality.
* **Immutable.** Every state change returns a new instance.
* **Self-validation.** The constructor or the factory method checks every
  required attribute with `Validate` from the module `validation`. Missing or
  invalid values result in a `ValidationException` with the attribute name;
  steps that are forbidden by the business rules result in
  `IllegalStateTransition`. Only the type checks: query methods, use cases and
  adapters do not check their parameters
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* **Creating and restoring.** Factory methods such as `create` create new
  objects; `restore` restores saved ones. Both check all rules.
* **Time.** The model reads no clock. Methods that need a time
  get `now` as a parameter.
* **Personal data.** `toString` outputs no data context, neither in the
  domain model nor in the SPI.
* **Packages per aggregate.** Within `domain-model` there is one package per
  aggregate: `template` (letterhead and letter template), `snapshot` and
  `letter`. Letterhead and letter template share a package because they have
  the same version rules; the `VersionSequence` that enforces them thus stays
  package-internal. What only one aggregate needs lives in its package and is
  encapsulated there as far as possible. The value types that several aggregates
  and the ports share (`UserId`, `BusinessReference`, `DataContext`, `Checksum`,
  `TemplateAction` and `LetterAction`) live in the root package
  `domain.model`. There is no further split by roles (entities, value objects),
  and no aggregate gets a Gradle module of its own (owner, 2026-11-21). ArchUnit
  checks that the aggregate packages form no cycle and that the root package
  knows none of them.

== Placeholders

Syntax `${pfad.zum.wert}`, defaults, repeat and condition blocks; missing
values stay visible (xref:adr-008-platzhaltersprache[ADR-008]). The host
provides values already formatted.
