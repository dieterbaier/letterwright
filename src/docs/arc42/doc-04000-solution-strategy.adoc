== Code Style

The architecture defines how the code is written. For known patterns it refers
to the source instead of retelling it:

* *The code says the how, the documentation the why* (Robert C. Martin,
  _Clean Code_). Names and signatures carry the meaning. At the SPI, the
  Javadoc fully describes how to use the interface, because it is the
  contract with the host. In the rest of the code, Javadoc appears only where it
  explains a reason or a rule that the signature cannot express.
* *Ubiquitous Language* (Eric Evans, _Domain-Driven Design_): types and methods
  are named as in the xref:glossary[glossary].
  xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018] defines
  the DDD roles.
* *Static factory methods instead of constructors* (Joshua Bloch, _Effective Java_,
  Item 1): `create`, `fromSnapshot`, `generate()` and `restore` say what an
  object is created for (xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018]).
* *Illegal states are unrepresentable* (Yaron Minsky, “Make illegal states
  unrepresentable”): what a type can express, nobody checks at runtime.
  Sealed types and records replace flags and optional fields
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Validate where the value is created* (Alexis King, “Parse, don't validate”): the
  type checks itself on creation. Use cases and adapters trust it
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Null contract:* every package is `@NullMarked` (JSpecify); NullAway enforces
  this at compile time. An optional result is an `Optional`, never `null`;
  `Optional` is neither a field nor a parameter
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Business rejections are results, not exceptions* (Scott Wlaschin,
  “Railway Oriented Programming”): a use case returns every expected
  rejection, such as “not allowed” or “unknown”, as a separate case of a sealed
  type; the model is `PreviewResult`. The inbound adapter distinguishes them
  with a `switch` without `default`, so that the compiler reports a new case.
  Technical errors such as a failed store or a violated host contract remain
  exceptions and are not relabeled as business rejections. Decided by the owner
  in the review of PR #63.

* *Linting in backend and frontend:* in the frontend ESLint checks, in the
  backend Error Prone with its checks that are active by default. An exception
  is switched off individually and with a rationale
  (xref:adr-011-qualitaetsgates-im-build[ADR-011]).
* *Tests belong to their class* (Gerard Meszaros, _xUnit Test Patterns_,
  “Testcase Class per Class”): whoever starts from a production class finds
  its tests without searching. Decided by the owner in #65. In the backend:
** Every class with a business or technical contract of its own has a test
   class of the same name in the same package (`Foo` → `FooTest`). It checks
   the class's observable behavior. There are no collective test classes for
   several production classes.
** An internal helper, such as a package-private class, is tested through its
   callers, and in a targeted way.
** Pure data carriers without behavior of their own need no test class of their
   own: interfaces, enums without logic and exceptions without logic. Business
   invariants of a record, however, count as behavior of its own.
** A use case is tested in the test class of its implementation, for example
   `SaveLetterService` in `SaveLetterServiceTest`. This class is also
   the bridge to the Gherkin specification: the feature file names it in its
   header, and every test method is named like its scenario.
** A test that checks several classes together is named after the behavior it
   checks. Examples are `BuiltInAuthorizationCheckTest` and the
   architecture tests.
** Expected values are created in the test independently of the production code
   that computes them. If a test builds the expected SPI request with the same
   mapper that the adapter uses, for example, an error in the mapper stays
   invisible.

The skill `skills/code-stil/SKILL.md` describes how an agent applies these rules
when writing code.
