[[loesungsstrategie-code-stil]]
== Code-Stil

Die Architektur gibt vor, wie der Code entsteht. Für bekannte Muster verweist sie
auf die Quelle, statt sie nachzuerzählen:

* *Der Code sagt das Wie, die Dokumentation das Warum* (Robert C. Martin,
  _Clean Code_). Namen und Signaturen tragen die Bedeutung. Am SPI beschreibt die
  Javadoc vollständig, wie die Schnittstelle zu benutzen ist, denn sie ist der
  Vertrag mit dem Host. Im übrigen Code steht sie nur, wo sie einen Grund oder eine
  Regel erklärt, die die Signatur nicht ausdrücken kann.
* *Ubiquitous Language* (Eric Evans, _Domain-Driven Design_): Typen und Methoden
  heißen wie im xref:glossary[Glossar]. Die DDD-Rollen legt
  xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018] fest.
* *Statische Fabrikmethoden statt Konstruktoren* (Joshua Bloch, _Effective Java_,
  Item 1): `anlegen`, `ausSnapshot`, `neu()` und `wiederherstellen` sagen, wofür
  ein Objekt entsteht (xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018]).
* *Illegale Zustände sind nicht darstellbar* (Yaron Minsky, „Make illegal states
  unrepresentable“): Was ein Typ ausdrücken kann, prüft niemand zur Laufzeit.
  Sealed Types und Records ersetzen Flags und optionale Felder
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Validieren, wo der Wert entsteht* (Alexis King, „Parse, don't validate“): Der
  Typ prüft sich beim Erzeugen. Anwendungsfälle und Adapter vertrauen ihm
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Null-Vertrag:* Jedes Paket ist `@NullMarked` (JSpecify), NullAway setzt das beim
  Kompilieren durch. Ein optionales Ergebnis ist ein `Optional`, nie `null`;
  `Optional` ist kein Feld und kein Parameter
  (xref:adr-019-validierung-in-den-typen-und-null-vertrag[ADR-019]).
* *Fachliche Ablehnungen sind Ergebnisse, keine Ausnahmen* (Scott Wlaschin,
  „Railway Oriented Programming“): Ein Anwendungsfall gibt jede erwartbare
  Ablehnung, etwa „nicht erlaubt“ oder „unbekannt“, als eigenen Fall eines Sealed
  Type zurück, Vorbild `Vorschauergebnis`. Der eingehende Adapter unterscheidet sie
  mit einem `switch` ohne `default`, damit der Compiler einen neuen Fall meldet.
  Technische Fehler wie ein ausgefallener Speicher oder ein verletzter
  Host-Vertrag bleiben Ausnahmen und werden nicht zu fachlichen Ablehnungen
  umetikettiert. Entschieden vom Owner im Review von PR #63.

* *Linting in Backend und Frontend:* Im Frontend prüft ESLint, im Backend Error
  Prone mit seinen standardmäßig aktiven Prüfungen. Eine Ausnahme wird einzeln
  und mit Begründung abgeschaltet
  (xref:adr-011-qualitaetsgates-im-build[ADR-011]).

Wie ein Agent diese Regeln beim Schreiben von Code anwendet, beschreibt der Skill
`skills/code-stil/SKILL.md`.
