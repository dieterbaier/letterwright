= Glossary

The glossary is bilingual
(xref:adr-024-sprache-der-ubiquitous-language-im-code[ADR-024]). The first
column, “German term”, names the German term of the domain language. The
second column, “English term”, names the binding English term used in code,
features and documentation. Each German term has exactly one English term; a
synonym in code is a bug. The column “In code” names the identifier and its
DDD role
(xref:adr-018-ddd-rollen-und-selbstvalidierung-im-fachmodell[ADR-018]). Value
objects without a domain term of their own, such as `VersionNumber` or the IDs,
appear only in code.

[cols="2,2,5,3", options="header"]
|===
| German term | English term | Definition | In code
| Briefpapier | letterhead | Template for the page layout of a letter (header with logo and slogan, sender, address field, information block, footer, page numbers). Type private or business (DIN 5008 form A or B). | `Letterhead` (Aggregate Root), type `LetterheadType`
| Standardschreiben | letter template | Template for the content of a letter with placeholders; exactly one letterhead is assigned to it. It belongs to exactly one reference type. | `LetterTemplate` (Aggregate Root)
| Bezugstyp | reference type | The kind of business references for which letters may be created from a letter template, e.g. customer. The same value as the type of the business reference. | `LetterTemplate.referenceType()`, checked with `matches`
| Schreiben | letter | A document (PDF) created from a letter template with concrete data and saved. In the issue: “saved letter template”. There is at most one letter per snapshot. Visible until it is logically deleted; for users, a logically deleted letter no longer exists. | `Letter` (Aggregate Root), state `LetterState` (`Visible`, `LogicallyDeleted`); use cases `SaveLetter`, `ListLetters`, `DownloadLetter`, `DeleteLetter` with the results `SaveResult`, `ListResult`, `DownloadResult`, `DeletionResult`
| Übersicht | letter list | The visible letters for a business reference, page by page, newest first. What the user may not see counts neither in the page nor in the total count. | use case `ListLetters`; Value Objects `PageRequest` and `Page`
| Vorlage | template | Umbrella term for letterhead and letter template. | In compound names such as `TemplateId`, `TemplateVersion`, `TemplateRepository` and `TemplateAction`
| Vorlagenversion | template version | Immutable state of a letterhead or letter template with content and sample data; state draft, published, superseded or withdrawn. At most one version per template is published; new letters are created with it. A version is superseded when a newer one has been published; withdrawn when it was taken back without a successor (xref:adr-022-eine-veroeffentlichte-version-je-vorlage[ADR-022]). | `TemplateVersion` (entity in the template aggregate), state `TemplateVersionState`, reference `VersionReference`; use cases `PublishTemplateVersion` and `WithdrawTemplateVersion` with the results `PublicationResult` and `WithdrawalResult`
| Beispieldaten | sample data | Values for the placeholders of a template version that the template manager maintains with the draft. They fill the proof PDF and become immutable with the version. | `TemplateVersion.sampleData()`, a `DataContext`
| Probe-PDF | proof PDF | PDF that is created with its sample data before a template version is published and is checked like a saved letter. For this, a letter template is merged with the published letterhead, and a letterhead with built-in sample content. | `Renderer.createPdf`, `Renderer.createProofPdf`
| Baustein | building block | Delimited part of a letterhead or letter template (e.g. address field, subject, repeat block). |
| Platzhalter | placeholder | Expression such as `${recipient.name}` that is replaced during merging by a value from the data context; optionally with a default value. |
| Datenkontext | data context | The values the host provides for a letter template and a business reference, already formatted. | `DataContext` (Value Object); in the SPI `spi.DataContext`, requested with `DataRequest`
| Fachlicher Bezug | business reference | The domain object for which a letter is created (e.g. customer, case), as type and ID. The host assigns the ID as a key that is unique per reference type, canonical and permanently stable, and that the library does not interpret; if the host needs several keys, it encodes them into it itself without collisions. The library compares references by equality and saves them with every letter. | `BusinessReference` (Value Object); in the SPI `spi.BusinessReference`, in the Java API `api.BusinessReference`
| Vorschau | preview | Paginated HTML rendering of a filled letter template before saving. An updated preview replaces the snapshot of the previous one. | use case `CreatePreview`, result `PreviewResult`
| Snapshot | snapshot | Data context of a preview, saved for a limited time, from which the PDF is created on saving. Open until a letter is created from it; after that consumed and without data context. | `Snapshot` (Aggregate Root), state `SnapshotState` (`Open`, `Consumed`)
| Prüfsumme | checksum | SHA-256 checksum, for example of a saved PDF or of a data context. With it, saving detects a data context that changed since the preview, and the download delivers only an unchanged PDF. | `Checksum` (Value Object)
| Benutzerkennung | user ID | Identifier of the logged-in user as the host application provides it. The library does not manage users. | `UserId` (Value Object); in the SPI the attribute `userId` of the requests
| Dokumentverweis | document reference | Reference to the stored PDF of a letter; only the document store knows its meaning. | `DocumentReference` (Value Object)
| Host-Anwendung | host application | The Spring Boot/React application in which letterwright is embedded. |
| SPI | SPI | Service Provider Interface: the interfaces and data types in the module `spi` that the host application implements or provides (placeholder data, permission, deletion policy). Besides the Java API (module `api`, ADR-023) the only part of the library the host compiles against. Optionally, the letter save callback is added (`LetterSaveCallback`). | package `dieterbaier.letterwright.spi`
| Java-API | Java API | The use cases and data types in the module `api` that the host calls in its own code and in its own transaction (xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]). Today only “save letter”: the call joins a running transaction (`REQUIRED`), and the host receives the saved letter with ID, business reference, version of the letter template, user ID and time of creation, or a business rejection. Besides the SPI the only part of the library the host compiles against. | package `dieterbaier.letterwright.api`: `SaveLetter`, result `SaveResult`, data `SavedLetter` and `LetterTemplateVersion`; implemented by `ApiSaveLetter` in `adapter-api`
| Platzhalterdaten-Anbieter | placeholder data provider | Part of the SPI: provides the data context to the core. The host must provide it. | `PlaceholderDataProvider`; internally the port `PlaceholderDataSource`
| Berechtigungsprüfung | authorization check | Part of the SPI: decides whether a user may perform an action. Without an implementation of its own by the host, the role check of the starter applies. | `AuthorizationCheck`, request `AuthorizationRequest` (`ForTemplates`, `ForLetter` or `ForCreation`); internally the port `Permissions`
| Aktion | action | An act for which the host grants the permission: edit templates, publish templates (including withdrawing), create, view, download, delete letters. The actions for letters relate to a business reference, those for templates do not; creating also involves the letter template. Their type says so. | Value Objects `TemplateAction` and `LetterAction` (without creation); the same in the SPI, creation as the request `ForCreation`
| Löschrichtlinie | deletion policy | Part of the SPI: decides whether and how a letter is deleted. The host must provide it (RB-10). | `DeletionPolicy`, request `DeletionRequest`; internally the port `DeletionRules`
| Löschentscheidung | deletion decision | Answer of the deletion policy: hard delete (remove letter and PDF), logically delete (no longer show, PDF remains) or blocked (do not delete, with a reason for the user). | `DeletionDecision` (Value Object) with `hard()`, `logical()`, `blocked(reason)`; in the SPI `spi.DeletionDecision`
| Rückruf nach dem Speichern | letter save callback | Optional part of the SPI: when a user saves a new letter through the library's user interface, the library calls the host in the same transaction before the commit (xref:adr-023-speichern-in-einer-transaktion-des-hosts[ADR-023]). The host receives the ID of the letter, the business reference, the version of the letter template, the user ID and the time of creation. It accepts, or rejects with a reason for the user; then the shared transaction is rolled back. Only for a new letter, never via the Java API. Without an implementation by the host there is no callback. | `LetterSaveCallback` with `created(SavedLetter)` and `LetterTemplateVersion`; internally the port `SaveCallback`, implemented by `HostSaveCallback`
| Rückrufergebnis | callback result | Answer of the letter save callback: accepted, or rejected with a reason for the user. On saving, the rejection appears as a separate case of the result. | `CallbackResult` (Value Object) with `accepted()`, `rejected(reason)`; in the SPI `spi.CallbackResult`; in the result of saving `SaveResult.RejectedByHost`
| Sachbearbeiter | clerk | User who creates, saves, downloads and deletes letters. |
| Vorlagenverwalter | template manager | Business user who maintains letterheads and letter templates. |
| Form A / Form B | form A / form B | Variants of the DIN 5008 business letter with different heights of the address field; default form B. | `LetterheadType.BUSINESS_FORM_A`, `BUSINESS_FORM_B`
| PDF/A | PDF/A | ISO standard for PDFs suitable for long-term archiving; here part 2, level b. |
| PDF/UA | PDF/UA | ISO standard for accessible PDFs; here PDF/UA-1. |
|===

[[document-terms]]
== Document Terms

Four general terms describe how letterwright produces a document. They place
the terms of the table above in the host's view and do not replace them.

[cols="2,5,3", options="header"]
|===
| Term | Meaning | In letterwright
| document type | The business kind of document, for example order confirmation. It belongs to the host and is named in the host's language. | No term of its own; the host maps it to a document template
| document template | Template for the content of a document with placeholders; it references a layout template. | letter template, `LetterTemplate`
| layout template | Template for the page layout of a document. | letterhead, `Letterhead`
| generated document | Document produced from a document template, its layout template and the business data. | letter, `Letter`
|===

The host selects the document template and supplies it directly to
letterwright (xref:host-document-selection[system context]).
